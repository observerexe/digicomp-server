# DigiComp HUB — вимоги та план робіт

Nov 9, 2026 · @observer.exe

## Огляд

DigiComp HUB — вебзастосунок творчої групи (понад 10 людей, переважно з телефона). Бекенд у репо [observerexe/digicomp-server](https://github.com/observerexe/digicomp-server) вже покриває більшість модулів. Фронтенд пишемо з нуля, обидва старі фронти зносимо. Порядок: спершу доводимо сервер, потім фронт.

**Що є зараз**

| Частина | Стан |
| --- | --- |
| Сервер | Ubuntu Server, Docker Compose: PostgreSQL 17 + API (NestJS 12, TypeORM), порт 127.0.0.1:3000 |
| Доступ ззовні | Tailscale Funnel; зараз веде на старий Python-шлюз (порт 8765) |
| Home Assistant | На тому ж сервері, `network_mode: host`; API ходить до нього через `host.docker.internal:8123` |
| Безпека | argon2, JWT + одноразові refresh-токени, HttpOnly-cookie + CSRF для вебу, ліміти запитів, аудит |
| Дані | Міграції, щоденні бекапи бази й файлів, скрипт перевірки відновлення |
| Тести | Фактично немає (лише заготовки шаблону) |

**Що зносимо**

- `api/web` у репо (вебінтерфейс із коміту `1cbd5e6`). Бекендну частину того коміту — cookie-вхід, CSRF, заголовки безпеки — залишаємо.
- Старий окремий фронт (Python-шлюз `digicomp-hub`, порт 8765) на сервері: вимикаємо після запуску нового фронту, місце покаже власник.

**Стек нового фронту**

React + TypeScript + Vite, PWA (встановлюється на телефон як застосунок, камера для QR). Роздає його той самий NestJS з того ж домену, тому cookie-вхід і CSP працюють без змін. Типи API генеруються з OpenAPI (`/docs`), щоб фронт не розходився з бекендом.

## Ролі та права

Системних ролей три: `admin`, `moderator`, `member`. Роль `guest` прибираємо, `coordinator` перейменовуємо на `moderator`. Керівник групи — модератор. Спеціальність і посада лише описують людину і на права не впливають.

| Дія | admin | moderator | member |
| --- | --- | --- | --- |
| Розширена панель (метрики, логи, бекап, перезапуск) | так | ні | ні |
| Журнал усіх дій (аудит) | так | ні | ні |
| Видати або передати адмінку | так | ні | ні |
| Скинути пароль іншому | так | ні | ні |
| Змінити ім'я іншого | так | ні | ні |
| Видалити недоречний аватар чи біо іншого | так | ні | ні |
| Понизити чи заблокувати модератора | так | ні | ні |
| Створити учасника з паролем | так | так | ні |
| Заблокувати (вигнати) учасника | так | лише member | ні |
| Підвищити member до moderator | так | так | ні |
| Змінити спеціальність і посаду іншого | так | так | ні |
| Змінити своє біо й аватар | так | так | так |
| Бали, штрафи, догани, попередження | так | так, не собі | ні |
| Зняти такий запис | так | лише свій, з причиною | ні |
| Створити ТЗ, проєкт | так | так | ні |
| Взяти ТЗ і здати на рев'ю | так | так | так |
| Прийняти ТЗ (нарахування балів) | так | так, не своє | ні |
| Оновити етап і прогрес проєкту | так | так | якщо учасник |
| Документи, обладнання, довідник складу | так | так | перегляд |
| Видати допуск до обладнання | так | так | ні |
| Склад: взяти або поповнити | так | так | так |
| Сеанс роботи з обладнанням | так | так | з допуском |
| Завершити чужий сеанс | так | так, з причиною | ні |
| Бронювання | так | так, скасовує будь-яке | своє |
| Звіт про несправність | так | так, закриває | створити |
| Розумні пристрої: керувати / список дозволених | так / так | так / ні | перегляд / ні |

**Правила проти підстав**

- Пароль скидає лише адмін: інакше модератор міг би увійти від чужого імені.
- Модератор не нараховує бали собі і не приймає ТЗ, де сам виконавець. Адмін не обмежений нічим.
- Записи не видаляються, а знімаються з причиною; усе пишеться в аудит.
- Адмін завжди є хоча б один (це правило вже є в бекенді). Модератор не може діяти над іншим модератором чи адміном, окрім нарахування балів і дисципліни.

## Модулі

У кожному модулі: що він робить, що вже є в бекенді і що треба додати.

### 1. Команда

- Список учасників картками: аватар, ім'я, посада, спеціальність, біо. Пошук і фільтр за спеціальністю.
- Є: усі поля, аватари, блокування, захист останнього адміна.
- Додати: нові ролі та права з розділу вище; member змінює в себе лише біо й аватар.

### 2. Обладнання, журнал, бронювання, несправності

- У кожної одиниці є сторінка з QR. Скан або вибір у застосунку → «Почати роботу» → «Завершити». Час ставить сервер.
- Є: місця з QR-кодами, допуски з терміном, сеанси, підтвердження техніки безпеки, статус «на обслуговуванні».
- Додати вивантаження журналу: обладнання, особа, час початку, час кінця, тривалість. Фільтри: період, обладнання, особа. Формати: CSV і сторінка для друку / PDF.
- Додати автозакриття забутих сеансів з позначкою «закрито автоматично».
- Додати бронювання: календар по кожній одиниці, без перетинів часу. Хтось інший не може почати сеанс у чужий слот.
- Додати звіти про несправність: опис + фото, статус «відкрито → в роботі → закрито». Модератор однією дією ставить обладнання на обслуговування.

### 3. Архів

- Є повністю: документи з версіями, категорії, пошук за назвою, прив'язка до обладнання й складу, доступ «всім» або «лише модераторам».
- Фронт: перегляд PDF і картинок прямо в застосунку, завантаження перетягуванням.

### 4. Smart-лабораторія

- Є: світло (увімкнення, яскравість), сцени, датчики; список дозволених пристроїв веде адмін. Розетки й вимикачі свідомо заборонені.
- Фронт: сторінка по кімнатах, плитки з перемикачами і повзунком яскравості.

### 5. Принтери

Відкладено (див. останній розділ).

### 6. [x] Склад (позиція відкривається за кодом з QR; наліпки складу на тій самій сторінці, що й обладнання)

- Є: позиції, рухи з коментарем, низький залишок, CSV, захист від дублів.
- Додати: member може поповнювати (зараз лише брати). QR-наліпки на позиції, щоб взяти річ сканом.

### 7. Проєкти

- Учасники, опис, файли, історія змін — є.
- Додати: дата початку, дедлайн, етап із фіксованого списку замість вільного тексту. Проєкти і ТЗ не пов'язані.
- Фронт: дошка колонками по етапах, картки з аватарами учасників, дедлайном і прогресом; перетягування між етапами.

### 8. ТЗ (дошка завдань)

- Дошка з чотирма колонками: «Вільне» → «В роботі» → «На перевірці» → «Виконано». Схема нижче.
- Модератор створює ТЗ: назва, опис, бали, дедлайн, максимум виконавців. Учасники самі беруть ТЗ і здають на перевірку.
- Модератор приймає або повертає на допрацювання з коментарем. Після прийняття бали діляться порівну між виконавцями.
- До ТЗ можна додати коментарі та файли. Зараз у бекенді є лише базові `tasks`: створює лише admin, кожен виконавець отримує повну суму.

### 9. Бали і дисципліна

- Усі бали записуються в одну книгу обліку (ledger, вже є). Джерела: ТЗ, побутова задача (ручне нарахування), штраф (мінус).
- Дисципліна — окрема таблиця: тип (попередження, штраф, догана), причина, хто видав, дата, сума штрафу. Терміну дії немає: модератор знімає запис вручну з причиною. Зняття штрафу повертає бали.
- Учасник бачить свої записи в профілі разом із тим, хто їх видав. Інші учасники їх не бачать.

### 10. Профіль

- Свій профіль: зміна біо, аватара й пароля; баланс і історія балів; попередження, штрафи, догани; мої ТЗ, проєкти, допуски, бронювання.
- Чужий профіль: лише публічне — аватар, ім'я, посада, спеціальність, біо, бали.

### 11. Рейтинг

- Таблиця з аватарами і топ-3 зверху. Перемикач «цей місяць / за весь час».
- Виправити: заблоковані учасники в рейтинг не потрапляють.

### 12. Панель керування (moderator і admin)

Учасники та ролі · нарахування балів · таблиця дисципліни · ТЗ на перевірці · допуски · обладнання й QR · склад · документи · бронювання · звіти про несправності · вивантаження журналу.

### 13. Розширена панель (лише admin)

- Перегляд: CPU, RAM, диск, аптайм, стан контейнерів (API, база, HA), останні рядки логів API, журнал аудиту, дата останнього бекапу.
- Дії зі списку: зробити бекап, перевірити відновлення, перезапустити API чи HA. Без shell, без видалення даних, без доступу API до docker socket.
- Як: маленький агент на сервері (systemd) з фіксованим списком команд, слухає лише локально; API викликає його. Для admin додати 2FA (коди з додатка-автентифікатора).

## Дизайн і UX

Застосунок спершу робимо для телефона, а на комп'ютері він розгортається в ширший макет. Акцентний колір — синій.

- **Навігація.** На телефоні нижня панель з 5 вкладок: Головна, ТЗ, Скан QR (кнопка по центру), Лабораторія, Профіль. Решта в меню «Ще». На комп'ютері — бічна панель.
- **Головна.** Мій активний сеанс, мої ТЗ і дедлайни, мої бали, зайняте зараз обладнання, найближчі бронювання.
- **Стиль.** Світла і темна тема, заокруглені картки, великі зони натискання (не менше 44 px), один шрифт з кирилицею. Синій лише для головних дій і активних станів; зелений, жовтий, червоний — лише для статусів.
- **Плавність.** Анімації переходів 150–250 мс, скелетони замість порожніх екранів, миттєва реакція на натискання (оптимістичні оновлення), перетягування карток на дошці пальцем. Повага до системного налаштування «менше руху».
- **Помилки та порожні стани.** Людські тексти по коду помилки з бекенду (`errorCode`), а не «Щось пішло не так».
- **Друк.** Журнал обладнання друкується на A4 чистою таблицею без елементів інтерфейсу.
- **Як домовляємось про вигляд.** Перед фронтом робимо макети 3–4 ключових екранів (головна, дошка ТЗ, сторінка обладнання, профіль). Ви їх затверджуєте, і лише потім пишемо код.

Рішення етапу 2:

## Як працювати з Claude Code

На Arch зручніше за все розширення Claude Code для VS Code: це графічний чат сбоку від коду і перегляд змін до/після, термінал не потрібен. Десктопний застосунок Claude, за наявними джерелами, є лише для macOS і Windows. Потрібна платна підписка Claude (Pro або вище).

**Встановлення**

1. Встановити VS Code: `yay -S visual-studio-code-bin` (або через будь-який інший помічник AUR).
2. У VS Code натиснути Ctrl+Shift+X, знайти «Claude Code» від Anthropic, встановити, увійти в акаунт Claude. Розширення має власну копію Claude Code, окремо нічого ставити не треба.
3. Встановити Docker і Node.js: `sudo pacman -S docker docker-compose nodejs npm git`, потім `sudo systemctl enable --now docker` і `sudo usermod -aG docker $USER` (перелогінитись).
4. Склонувати репо і відкрити папку в VS Code (File → Open Folder).
5. Покласти в репо цей документ як `docs/PLAN.md` (експорт у Markdown) і файл `CLAUDE.md` у корінь — Claude Code читає його на початку кожної сесії.

**Як вести кожен етап**

1. Нова сесія для кожного етапу. Перше повідомлення: «Прочитай docs/PLAN.md, робимо етап N. Спершу склади план, код не пиши».
2. Прочитати план, поправити, сказати «роби».
3. Переглядати зміни, попросити запустити тести і лінтер.
4. Попросити зробити коміт і позначити пункти чек-листа в `docs/PLAN.md`.

Claude Code заходить на сервер (`ssh digicomp@digicomp`) лише в таких межах: читати можна, кожну зміну ви підтверджуєте окремо, без `sudo`. Те, що потребує root (агент панелі, `tailscale serve`), робите ви самі.

Джерела: [Claude Code для VS Code](https://code.claude.com/docs/en/vscode-extension), [про Linux і десктопний застосунок](https://neurohive.io/en/guides/claude-code-getting-started-guide/).

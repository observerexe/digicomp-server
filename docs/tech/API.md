# API DigiComp HUB

Загальні правила, вхід, помилки й поведінка, яку не видно зі схеми. Окремі ендпоінти з полями описує Swagger:
`/api/docs` (увійдіть адміном) або файл `api/openapi.json`. Права за ролями — [ARCHITECTURE.md](ARCHITECTURE.md#ролі-та-права).

## Загальні правила

- **Адреси.** Усе API — під `/api` (`/api/tasks`, `/api/auth/login`). У корені лише `/health`; решту адрес займають сторінки застосунку.
- **Дати** — ISO 8601 в UTC. Дні, місяці й дедлайни сервер рахує за київським часом.
- **Статуси успіху.** `POST`, що створює об'єкт, — 201; дії й решта запитів — 200; дії розширеної панелі — 202.
- **Списки** — `{ items, total, page, limit }` з `page` і `limit` у query. Масивом відповідають `/places`, `/tasks`, `/discipline/me`, `/audit`, `/bookings/me`, `/links/candidates`, рейтинг.
- **`:id` або код.** Для обладнання й позицій складу в шляху можна передати uuid або код з QR-наліпки (без різниці в регістрі).
- **Файли** — `multipart/form-data`, поле `file`. Документи й матеріали до 20 МБ, фото несправності до 5 МБ, аватар до 2 МБ (png, jpg, webp).
  Тип перевіряється за вмістом. Файли віддаються лише авторизованим.
- **Ідемпотентність.** Старт сеансу і рух на складі приймають `idempotencyKey` (8–64 символи): повтор з тим самим ключем повертає
  той самий результат без дубля. Новий ключ — на кожну дію людини.
- **Права в інтерфейсі** — список `permissions` у `GET /api/auth/me`. Правила, що залежать від цілі (над ким, чий запис), перевіряє лише сервер.

## Вхід

**Два режими.**

- **Застосунок (cookie).** З заголовком `X-DC-Client: web` вхід і `refresh` ставлять HttpOnly-cookie, тіло містить лише `user`.
  Кожен запит, що змінює дані, мусить нести `X-DC-Client: web`, інакше 403 `CSRF`.
- **Скрипти й інструменти (Bearer).** Без цього заголовка вхід повертає `accessToken` і `refreshToken`; далі `Authorization: Bearer <accessToken>`.

**Потік.**

- `POST /api/auth/login { email, password }`. Якщо в людини увімкнена 2FA — відповідь `{ twoFactorRequired: true, challengeToken }`,
  далі `POST /api/auth/2fa/verify { challengeToken, code }` або `{ challengeToken, recoveryCode }`. `challengeToken` діє 5 хвилин.
- `POST /api/auth/refresh` — новий токен доступу (1 год) і новий refresh (30 днів); старий refresh більше не діє.
- `POST /api/auth/logout` — цей пристрій; `POST /api/auth/logout-all` — усі.
- `POST /api/auth/setup` — створює першого адміна, лише поки в базі немає користувачів.

**2FA (свій акаунт).** `POST /api/auth/2fa/setup` → `{ secret, otpauthUri }`; `POST /api/auth/2fa/enable { code }` → 8 запасних кодів
(показуються раз) і закриття всіх сесій; `disable` і `recovery-codes` — з кодом. Адмін скидає 2FA іншому: `POST /api/users/:id/2fa/reset`.

## Помилки

Формат: `{ "statusCode": 409, "errorCode": "INSUFFICIENT_STOCK", "message": "Insufficient stock" }`.
Орієнтуйтеся лише на `errorCode`: `message` може змінитися, у помилках валідації це масив.

**Загальні:** `VALIDATION_ERROR` (400), `UNAUTHORIZED` (401), `FORBIDDEN` (403), `CSRF` (403), `NOT_FOUND` (404), `CONFLICT` (409),
`CONSTRAINT_VIOLATION` (409), `FILE_TOO_LARGE` (413), `RATE_LIMITED` (429), `INTERNAL_ERROR` (500), `SERVICE_UNAVAILABLE` (503).
«Не знайдено» для конкретних об'єктів: `USER_NOT_FOUND`, `TASK_NOT_FOUND`, `PLACE_NOT_FOUND`, `SESSION_NOT_FOUND`, `BOOKING_NOT_FOUND`,
`FAULT_REPORT_NOT_FOUND`, `DOCUMENT_NOT_FOUND`, `VERSION_NOT_FOUND`, `FILE_NOT_FOUND`, `ITEM_NOT_FOUND`, `PROJECT_NOT_FOUND`,
`AUTHORIZATION_NOT_FOUND`, `POINTS_ENTRY_NOT_FOUND`, `DISCIPLINE_RECORD_NOT_FOUND`, `SMART_DEVICE_NOT_FOUND`, `AUDIT_CURSOR_NOT_FOUND`,
`DICTIONARY_NOT_FOUND`, `DICTIONARY_ITEM_NOT_FOUND`, `RECORD_TYPE_NOT_FOUND`, `FIELD_DEF_NOT_FOUND`, `LINK_NOT_FOUND`,
`RECORD_NOT_FOUND` (запису немає або людина його не бачить), `PAPER_NOT_FOUND` (документа редактора немає або людина його не бачить),
`TEMPLATE_NOT_FOUND` (шаблону немає або учасник його не бачить), `TEMPLATE_VERSION_NOT_FOUND`.

## Поведінка, яку не видно зі схеми

### Учасники

- `PATCH /api/users/me`: `bio` — усі; `position`, `specialty` — admin і moderator; `name` — лише admin. Надіслане без змін поле помилки не дає.
- `PATCH /api/users/:id`: ім'я, email, біо — admin; посада, спеціальність, `active` — admin і moderator (moderator лише для `member`);
  `member → moderator` — admin і moderator, `moderator → member` і будь-що з `admin` — лише admin.
- Списки показують усім публічну картку; admin і moderator бачать ще `email`, `active`, `twoFactorEnabled`, `createdAt`.
- Нова адреса аватара містить `?v=<час>`, тож браузер не показує старий з кешу.

### ТЗ

    todo (Вільне) → queued (В черзі) → in_progress (В роботі) → review (На перевірці) → done (Виконано)
                                              ↑──────── return (з коментарем) ─────────┘

- Виконавців не призначають: беруть самі (`take`) у `todo` і `queued`, поки є місця; перший переводить ТЗ у `queued`.
- `start` — будь-який виконавець; після цього приєднатися не можна. `leave` — у `queued` чи `in_progress`; якщо пішов останній, ТЗ знову `todo`.
- `submit` → `review`; `return { body }` → `in_progress` з обов'язковим коментарем; `accept` → `done` і бали.
- Бали діляться порівну, остача — по балу тим, хто взяв раніше; нульові частки не записуються.
- `GET /api/tasks?status=&mine=true&limit=` — масив; для `done` спершу останні виконані.
- `extra` — додаткові поля ТЗ (див. «Додаткові поля»): у `POST` — усі обов'язкові; у `PATCH` змінюються лише передані ключі, `null` очищає.
- `submittedAt` — коли ТЗ востаннє здали на перевірку; `completedAt` — коли прийняли; `acceptedById` — хто прийняв (`null`, якщо ще ні
  або людини вже немає).
- ТЗ, створене документом (див. «Документи редактора»: публікація), `DELETE` не видаляє — 409 `TASK_HAS_PAPER`; його знімає скасування документа.

### Бали й дисципліна

- Книга балів лише доповнюється; зняття (`POST /api/points/:id/revoke { reason }`) додає компенсаційний запис. Знімається лише ручне нарахування.
- Штраф (`type: fine`, `amount`) одразу знімає бали; зняття штрафу їх повертає. Записи не видаляються, а позначаються `revoked`.
- Рейтинг (`/api/points/leaderboard?period=month|all`): однакова сума — однакове місце, заблокованих немає,
  місяць — календарний за Києвом, зняті записи не враховуються.
- Учасник бачить лише свої записи дисципліни (`/api/discipline/me`).

### Обладнання

- Сеанс: `safetyConfirmed: true` обов'язково, час ставить сервер. admin і moderator можуть без допуску.
  Під час чужого бронювання почати не можна (`PLACE_BOOKED`), крім admin.
- Сервер раз на 10 хвилин закриває сеанси, довші за 12 годин (`SESSION_AUTO_CLOSE_HOURS`): кінець = початок + 12 год, `autoClosed: true`.
- `GET /api/places/:id/sessions/recent` — останні 10 сеансів для всіх, без нотаток.
- Журнал: `GET /api/work-sessions/export.csv` (UTF-8 з BOM, для Excel) і `/report` (сторінка A4 для друку) — admin і moderator,
  фільтри `from`, `to`, `placeId`, `userId`, без періоду — поточний місяць, до 5000 сеансів.
- Бронювання: не в минулому (допуск 5 хв), до 12 годин, до 60 днів наперед, лише для обладнання в роботі; member — лише з допуском,
  що діє до кінця слоту. Перетини неможливі навіть за одночасних запитів (гарантує база); суміжні слоти дозволені.
- Несправність: `open → in_progress → closed`; `maintenance` — одна дія «в роботі + обладнання на обслуговування»;
  `close { resolution, reactivatePlace }` може одразу повернути обладнання в роботу. До 3 фото.
- Допуск: `POST /api/place-authorizations { userId, placeId, expiresAt?, note? }`; повторна видача оновлює термін.

### Склад, документи, проєкти

- Залишок змінюється лише рухами (`POST /api/inventory/items/:id/movements { delta, note, projectId?, idempotencyKey }`).
  Брати й поповнювати можуть усі; `?lowStock=true` — позиції з низьким залишком.
- Документ: нова версія не змінює попередні; `DELETE` лише архівує. `download?inline=1` показує PDF у застосунку
  (вбудувати можуть лише його сторінки); інші типи лише завантажуються. Доступ `members` або `supervisors`.
  `?linkedType=place&linkedId=…` — лише документи, пов'язані з цим записом (див. «Зв'язки»); параметри йдуть лише парою.
- Проєкт: етапи `idea`, `planning`, `execution`, `review`, `done`; архів — `DELETE`. member редагує лише свої проєкти і не змінює склад учасників.

### Довідники

- `GET /api/dictionaries` — усі довідники з пунктами (архівні з `archived: true`), читають усі ролі; змінюють admin і moderator.
- У шляху — `key` довідника й пункту (`/api/dictionaries/typ_tz/items/dyzain`). Ключ сервер створює з назви при створенні
  й більше не змінює; записи зберігають саме ключ. `required: true` — на довідник спирається модуль, видалити його не можна.
- Колір пункту — назва з палітри: `gray`, `red`, `orange`, `yellow`, `green`, `teal`, `blue`, `purple` (за замовчуванням `gray`).
- Новий пункт стає в кінець. `PUT /api/dictionaries/:key/items/order { keys }` — новий порядок, у списку мають бути всі пункти, разом з архівними.
- `PATCH …/items/:itemKey { archived: true }` — в архів: пункт не пропонують для нових записів, у старих він лишається.
- Довідники модулів — категорії: `place_category` (обладнання), `document_category` (архів), `inventory_category` (склад).
  Поле `category` у `/places`, `/documents`, `/inventory/items` — ключ пункту; фільтр `?category=` — теж ключ,
  а `?search=` шукає за назвою пункту. У CSV складу — назва категорії.

### Схеми записів

- `GET /api/records/:type/schema` — поля типу записів: ключ (той самий, що в API запису), назва, тип, межі. Даних записів немає;
  читають усі ролі. Невідомий тип — 404 `RECORD_TYPE_NOT_FOUND`.
- Типи: `user`, `task`, `project`, `place`, `inventory_item`, `discipline_record`, `points_entry`, `place_authorization`;
  `session`, `fault`, `document`, `paper` — лише для читання (жодне поле не має `create` чи `update`).
- Тип поля: `text`, `richtext`, `int`, `decimal` (`scale` — знаків після коми), `date` (`YYYY-MM-DD`), `datetime`, `bool`,
  `enum`, `color`, `ref:<тип запису>` (UUID) або `list<…>` з одного з них. `enum` має або `options` (фіксовані значення з назвами),
  або `dictionary` (значення — ключі пунктів довідника).
- `required` — обов'язкове при створенні; `create` / `update` — поле можна задати при створенні / змінити потім;
  `nullable` — можна очистити; `source` — `column` (за замовчуванням), `relation` (окрема таблиця: виконавці ТЗ, учасники проєкту)
  `computed` або `extra` (додаткове поле, значення в `extra` запису).
- `extensible: true` — тип має додаткові поля (зараз лише `task`); вони йдуть у кінці `fields` у своєму порядку.
  Архівне додаткове поле має `archived: true` і не має `create` / `update`.
- `version` — короткий хеш опису; змінюється з будь-якою зміною схеми, зокрема додаткових полів.

### Додаткові поля

- Описові поля записів, які додають admin і moderator без коду («Налаштування полів»). Значення — в `extra` запису: `{ "typ": "dyzain" }`.
- `GET /api/records/:type/field-defs` — поля типу разом з архівними, по порядку; читають усі ролі. Тип без додаткових полів — 404 `RECORD_TYPE_NOT_FOUND`.
- `POST …/field-defs { label, type, required?, dictionary?, min?, max?, maxLength?, maxItems? }`. Ключ сервер створює з назви
  (як у довідниках) і не дає йому збігтися з ключами звичайних полів (`Points` → `points_2`); ключ, тип і довідник потім не змінюються.
- Типи й межі: `text` (`maxLength` 1–1000, за замовчуванням 200; пробіли по краях обрізаються), `int` і `decimal` (2 знаки після коми;
  `min`, `max` у межах ±10⁹), `date` (`YYYY-MM-DD`), `bool`, `enum` і `list<enum>` (обов'язковий `dictionary`; у списку — без повторів,
  `maxItems` 1–50, за замовчуванням 10; порожній список очищає поле). Межі, що не пасують типу, — 400 `VALIDATION_ERROR`;
  невідомий довідник — 404 `DICTIONARY_NOT_FOUND`.
- `PATCH …/field-defs/:key { label?, required?, min?, max?, maxLength?, maxItems?, archived? }`. Нові межі й обов'язковість
  діють для нових значень; уже збережені значення не перевіряються наново.
- Архівне поле: старі значення лишаються, нове не приймається (те саме значення надіслати знову можна, очистити — теж).
- `PUT …/field-defs/order { keys }` — новий порядок, у списку всі поля разом з архівними.
- `DELETE …/field-defs/:key` — лише якщо жоден запис не має значення в полі, інакше 409 `FIELD_DEF_IN_USE`.
- Довідник, з якого бере значення поле, не видаляється (`required: true`); пункт, що стоїть в `extra`, теж (`DICTIONARY_ITEM_IN_USE`).

### Зв'язки

- Пов'язати можна записи типів `task`, `project`, `place`, `inventory_item`, `document`, `user`, `paper`; інші — 400 `LINK_TYPE_INVALID`.
  Від учасника (`user`) і документа редактора (`paper`) вручну не пов'язують (403 `FORBIDDEN`): учасника згадують документи,
  а зв'язки документа пише його збереження (див. «Документи редактора»). До них пов'язувати можна, як до будь-якого видимого запису.
- `GET /api/links?type=&id=` — `{ canLink, items }`: `canLink` — людина редагує цей запис, тож може пов'язувати його з іншими;
  `items` — зв'язки запису в обидва боки, від найстаріших. У кожному: `direction` (`out` — запис є джерелом,
  `in` — джерело інший запис), `type`, `recordId`, `title`, `archived` другого запису, `code` (QR-код — лише в обладнання
  й позиції складу, за ним відкривається сторінка), `role`, хто й коли створив, `canRemove`. Записи, яких людина не бачить (документ «лише модератори», архівне обладнання для учасника, архівний проєкт), не потрапляють
  у список; якщо людина не бачить сам запис — 404 `RECORD_NOT_FOUND`. Учасник для учасника видно, якщо той активний
  (заблокованого бачать admin і moderator, з `archived: true`); документ редактора — за правилами документів, скасований — `archived: true`.
- `POST /api/links { fromType, fromId, toType, toId, role? }` — зв'язує той, хто може редагувати джерело (`from`): ТЗ, обладнання,
  склад, документи архіву — admin і moderator; проєкт — ще й учасник проєкту (інакше 403 `PROJECT_EDIT_FORBIDDEN`).
  Обидва записи мають бути видимі цій людині. `role` — ключ (`a-z`, цифри, `_`, до 40 знаків), за замовчуванням порожній.
  Та сама пара з тією самою роллю — один раз, у будь-якому напрямку (`LINK_DUPLICATE`).
- `GET /api/links/candidates?type=&q=` — записи типу, які людина бачить, для вибору, що пов'язати: до 20, за назвою;
  `q` (до 100 знаків) шукає в назві, а в обладнання й складу — ще й у коді; учасники — лише активні, за ім'ям. Кожен — `{ id, type, title, archived, code? }`.
  Ним же шукають пікери полів `ref:*` і «@» у редакторі.
  Пов'язані вже записи не відкидаються — це робить клієнт.
- `DELETE /api/links/:id` — той, хто може редагувати джерело.
- Видалене ТЗ і видалена чернетка забирають свої зв'язки. Аудит: `link.created`, `link.removed` на записі-джерелі
  (зв'язки документа редактора — без окремого запису, вони йдуть зі збереженням документа).

### Реквізити

- Дані для документів: `GET /api/org-settings` — `{ institution, groupName, signer, signerPosition, updatedAt }`, читають усі ролі.
  `institution` і `groupName` — шапка документа (друкуються як записані), `signer` — підписант за замовчуванням
  `{ id, name, active }` або `null`, `signerPosition` — посада під підписом (окремо від посади в профілі).
- `PATCH /api/org-settings { institution?, groupName?, signerId?, signerPosition? }` — admin і moderator; змінюються лише передані поля,
  пробіли по краях обрізаються, порожній текст — 400 `VALIDATION_ERROR`. Підписант — активний учасник будь-якої ролі
  (модератор може вибрати й себе), інакше 400 `ORG_SIGNER_INVALID`; `signerId: null` — без підписанта.
- Заблокований підписант лишається (`active: false`), поки його не замінять; видалений — очищається.
  Аудит: `org_settings.updated` з тим, що змінилось (`changes`: було → стало); без змін запису немає.

### Документи редактора

- Документ — `{ id, title, number, status, visibility, author, revision, publishedAt, createdAt, updatedAt }`; окремий документ ще має
  `content` (документ ProseMirror, `{ "type": "doc", "content": [...] }`), `values` (значення полів шаблону за ключами),
  `template` (`null` — вільний документ), `refs`, `targetType` і `targetId` (запис, який документ створив; лишаються й після скасування),
  `cancelReason`, `canEdit` (людина може змінити й видалити його), `canPublish` і `canCancel` (може опублікувати чи скасувати;
  для документа, що створює запис, права на сам запис перевіряються під час дії).
  - `number` — `<префікс>-<рік>-<номер>` (`ТЗ-2026-014`): видається під час публікації, якщо в шаблону є `numberPrefix`; рік — за київським
    часом, номер — наступний для префікса в цьому році, щонайменше три цифри.
  - `refs` — записи, на які посилається документ (значення полів `ref:*` і «@» у тексті), як їх бачить людина:
    `{ type, id, title, archived, code? }`. Запису, якого людина не бачить або якого вже немає, у списку немає — редактор і друк
    показують «запис недоступний».
  - `template` — `{ id, title, version, kind, target, fields }`: шаблон і номер версії, з якої зроблено документ (документ лишається на ній, навіть коли
    опубліковано новішу), його вид і тип запису. Поле — `{ key, label, type, required, fill, editable, print, min, max, maxLength, maxItems, scale, options, plain, binding, canFill }`:
    межі — тісніші з поля шаблону й прив'язаного поля запису; `scale` — знаків після коми для `decimal` (`null` — 2);
    `options` — варіанти `enum` і `list<enum>` по порядку, `{ key, label, archived? }` (з довідника або схеми запису; для інших типів — `null`);
    `plain` — зона, прив'язана до текстового поля запису; `binding` — ключ поля запису, до якого прив'язане поле;
    `canFill` — людина може заповнити поле зараз.
  - Опублікований (не скасований) документ, що створив запис, показує в прив'язаних полях і зонах запис таким, яким він є зараз
    (`values`, `content` і друк); неприв'язані — як записали. Якщо запису вже немає — записані значення.
    Версію шаблону тут бачить кожен, хто бачить документ.
- `status`: `draft` (Чернетка), `published` (Опубліковано), `frozen` (Зафіксовано), `signed` (Підписано), `cancelled` (Скасовано).
  Документ створюється чернеткою; `publish` робить його опублікованим, `cancel` — скасованим (фіксація й підпис — пізніші етапи).
  `visibility`: `author` (автор і модератори) або `members` (усі учасники).
- Хто бачить: admin і moderator — усі документи, зокрема чужі чернетки; учасник — свої, опубліковані з `visibility: members` і опубліковані,
  чий запис людина бачить (так вирішує модуль запису; ТЗ бачать усі — отже, і їхні документи).
  Чернетку з `members` бачать лише автор і модератори, доки її не опубліковано. Чужий невидимий документ — 404 `PAPER_NOT_FOUND`.
- `GET /api/papers?mine=true&search=&page=&limit=` — без `content`, від нещодавно змінених; `mine=true` — лише свої,
  `search` (до 100 знаків) шукає в назві й номері.
- `POST /api/papers { title?, content?, templateId? }` — створити може будь-хто. Без назви — «Без назви», без вмісту — один порожній абзац.
  З `templateId` — документ з поточної версії шаблону: вміст — її тіло, значень немає, назва (якщо не передана) і видимість — з шаблону;
  `content` разом із `templateId` — 400. Шаблон має бути таким, з якого людина може створювати документи (як у `GET /api/papers/templates/:id`),
  опублікованим і не в архіві (інакше 404 `TEMPLATE_NOT_FOUND`); зламаний (`needsUpdate`) — 409 `TEMPLATE_NEEDS_UPDATE`. Відповідь — 201 з `content`.
- `POST /api/papers/:id/copy { title?, content, values? }` — копія документа, який людина бачить: нова чернетка людини з переданим вмістом і
  значеннями (так зберігають свій текст, коли оригінал змінив хтось інший). Версія шаблону — та сама, що в оригіналу; шаблон має бути доступним,
  як для створення. Вміст і значення перевіряються, як у `PATCH`. Без назви — назва оригіналу.
- `PATCH /api/papers/:id { revision, title?, content?, values?, visibility? }` — змінюються лише передані поля, відповідь — без `content`.
  `revision` — та, яку клієнт отримав останньою; інша — 409 `PAPER_CONFLICT`, документ не змінюється. Кожна зміна збільшує `revision`,
  запит без змін — ні.
  Назву, вміст і значення змінює автор (admin — будь-чий документ), лише в чернетці (інакше 409 `PAPER_NOT_DRAFT`); модератор чужу чернетку
  лише читає (403 `NOT_OWNER`). `visibility` змінюють admin і moderator; вона діє, коли документ опубліковано.
  - `values` — усі значення разом: ключ, якого немає, спорожнюється; `null`, порожній рядок і порожній список — теж «порожньо».
    Ключ — поле версії, крім `richtext` (зона пишеться у вмісті). Значення за типом:
    `text` — рядок без переносів (обрізається), до `maxLength` або 1000; `int` — ціле; `decimal` — до `scale` знаків; обидва в межах і до 10⁹ за модулем;
    `date` — `YYYY-MM-DD`; `datetime` — момент з поясом (зберігається в UTC); `bool`; `enum` — ключ варіанта; `color` — назва з палітри;
    `ref:<тип>` — UUID запису цього типу (малими літерами); `list<…>` — до `maxItems` або 20 значень свого типу, варіанти й записи без повторів.
    Вибрати можна чинний варіант; архівний лишається, де вже обраний. Новий для документа запис (його не було ні в значеннях, ні в тексті)
    має існувати й бути видимим людині (як у `GET /api/links/candidates`); запис, на який документ уже посилався, приймається й далі,
    навіть якщо його тим часом видалили.
    Обов'язковість тут не перевіряється (чернетка). Помилка — 400 `PAPER_FIELD_INVALID` з `field`. У вільного документа значень немає.
  - Поля з `fill: staff` (і їхні зони) змінюють лише admin і moderator (інакше 403 `NOT_ALLOWED`).
  - Вміст документа з шаблону — тіло версії, де змінюються лише вільні зони: інший текст, вузли поза зонами, поле в зоні, форматування в
    простій зоні — 400 `PAPER_CONTENT_LOCKED` (атрибути за замовчуванням, порядок позначок і поділ тексту на шматки значення не мають).
    Текст зони — до `maxLength` поля або 20 000 знаків (інакше `PAPER_FIELD_INVALID`). У вільному документі полів і зон немає.
  - Нове посилання «@» (`mention`) у вмісті — на запис, який існує й видимий людині, інакше 404 `RECORD_NOT_FOUND`; так само перевіряється
    вміст у `POST /api/papers` і `copy` (у копії записи оригіналу приймаються, як у його збереженні; пов'язуються ті, що є й видимі людині).
  - Зв'язки документа в `record_links` (`from_type: paper`) пише сервер у тій самій транзакції: поле `ref:*` — зв'язок з роллю — ключем поля,
    «@» — без ролі. Зайві зникають, коли значення чи посилання прибрано. Запис пов'язується, лише якщо відомо, що він є: щойно перевірений
    або вже пов'язаний з документом. Якщо пара вже пов'язана навпаки (від запису до документа), новий зв'язок не додається.
- `DELETE /api/papers/:id` — лише чернетку (інакше 409 `PAPER_NOT_DRAFT`), автор або admin.
- `POST /api/papers/:id/publish` — чернетка стає остаточною (інакше 409 `PAPER_NOT_DRAFT`). Публікує автор; admin і moderator — будь-чию.
  Відповідь — документ, як у `GET`. Усе в одній транзакції:
  - Обов'язкові поля мають значення, зони — текст (інакше 400 `PAPER_REQUIRED_MISSING` з `field`).
  - Документ шаблону `creates` створює запис через модуль цього типу — з його правами (ТЗ — admin і moderator, інакше 403), перевірками й аудитом.
    Значення беруться з прив'язаних полів (зона — текстом, абзац на рядок; додаткові поля — в `extra`). Помилка запису про поле повертається
    з тим самим `errorCode` і `field` — ключем поля шаблону (`PAPER_FIELD_INVALID`, `RECORD_EXTRA_INVALID`…). Якщо прив'язка версії вже
    зламалась — 409 `TEMPLATE_NEEDS_UPDATE`. Документ отримує `targetType`, `targetId` і зв'язок до запису з роллю `@target`
    (документ з'являється в «Пов'язаному» на сторінці запису).
  - Шаблон з `numberPrefix` дає номер. Вільний документ і документ `report` лише стають остаточними (прив'язка звіту до запису — етап 4.3).
- `POST /api/papers/:id/cancel { reason }` — скасувати опублікований документ (інакше 409 `PAPER_NOT_PUBLISHED`) з причиною (до 1000 знаків).
  Скасовує автор; admin і moderator — будь-чий. Опубліковані документи не видаляються. Документ, що створив запис, знімає й запис — за правилом
  модуля: ТЗ — лише admin і moderator, лише вільне без виконавців (інакше 409 `TASK_HAS_ASSIGNEES`); ТЗ видаляється, як `DELETE /api/tasks/:id`
  (аудит `task.deleted` з `reason`).
- `GET /api/papers/:id/print` — сторінка A4 для друку чи збереження в PDF (`text/html`, не JSON). Її бачить той, хто бачить документ
  (інакше 404 `PAPER_NOT_FOUND`). Друкується поточний вміст, а не знімок. Поля за ДСТУ 4163:2020 (ліве 30, праве 10, верхнє й нижнє 20 мм),
  номер сторінки — посередині вгорі, з другої сторінки. Шапка — назва закладу й групи з реквізитів; якщо обидві порожні, шапки немає.
  Назва документа — лише в заголовку вкладки. Сторінка має власний CSP: `default-src 'none'`, вбудований стиль дозволено хешем, шрифти — `'self'`, скриптів немає.
  «Авто: номер» друкується номером документа (до публікації — лінія).
  Поля друкуються значеннями (дата — `дд.мм.рррр`, час — київський, вибір — назвою варіанта, запис — назвою, список — через кому),
  «@» — назвою запису (невидимий чи видалений — «запис недоступний»); порожнє поле — лінія
  для запису від руки; поле з `print: false` (і його зона) у друк не потрапляє.
- Вміст перевіряється за спільним описом редактора (`shared/editor-schema/`): корінь `doc`, вузли `{ type, attrs?, content?, text?, marks? }`
  без інших ключів, мітки `{ type, attrs? }`; до 40 рівнів вкладеності й 50 000 вузлів. Інакше 400 `VALIDATION_ERROR`.
  - Вузли: `paragraph`, `heading` (`level` 1–3), `bulletList`, `orderedList` (`start`), `listItem`, `table`, `tableRow`, `tableCell` і
    `tableHeader` (`colspan`, `rowspan`, `colwidth` — лише `null`), `pageBreak`, `text`, `hardBreak`; поля шаблону — `field` (у рядку) і
    `fieldZone` (вільна зона, блок із блоками), обидва з обов'язковим `key` (ключ поля); посилання на запис — `mention` з обов'язковими
    `type` (тип запису, `a-z` і `_`) і `id` (UUID малими літерами), без назви; номер документа — `paperNumber` (без атрибутів).
    Кожен — лише в дозволеному місці: `text`, `hardBreak`, `field`, `mention` і `paperNumber` — в абзаці й заголовку, `listItem` — у списку, клітинки — у рядку, рядки — в таблиці; решта — блоки.
  - `paragraph` і `heading` мають `align` (`center`, `right`, `justify` або `null`) і `indent` (0–6, крок 5 мм).
  - Мітки: `bold`, `italic`, `underline`, `strike`, `textStyle` з `size` (10, 11, 12, 14, 16, 18, 20, 24, 28 pt), `color` (назва з палітри)
    і `font` (`serif`, `sans`); кожне — або `null`. Мітки лише на вузлах у рядку (`text`, `hardBreak`, `field`, `mention`, `paperNumber`).
  - Невідомі вузли, мітки й атрибути (зокрема `style` і `class`) не приймаються.
  Тіло запиту до `/api/papers` (зокрема шаблонів) — до 1 МБ (інакше 413).
- Аудит: `paper.created` (з шаблону — `templateId`, `version`; копія — `copyOf`), `paper.deleted` завжди; `paper.updated`
  (`changes`: назва, видимість; `content: true` і `values: true`, якщо змінено вміст чи значення) — коли змінено видимість або документ
  змінює не автор. Автозбереження автором своєї чернетки в аудит не пишеться. `paper.published` (`number`, `targetType`, `targetId`),
  `paper.cancelled` (`reason`, `number`, `targetType`, `targetId`) — завжди.
- Пункт довідника, обраний у полі документа (поле шаблону з `dictionary`), не видаляється (`DICTIONARY_ITEM_IN_USE`).

### Шаблони документів

- Шаблон — `{ id, title, kind, target, numberPrefix, autoFreeze, creators, visibility, archived, currentVersion, draftVersion, needsUpdate, createdAt, updatedAt }`;
  окремий шаблон ще має `versions` — `{ number, revision, publishedAt, publishedBy, updatedAt, documents }`, від нових;
  `documents` — скільки документів зроблено з версії (учасникові — `null`).
  - `kind`: `creates` (створює запис типу `target`), `report` (звіт про запис типу `target`), `free` (без запису, `target: null`).
    `creates` — лише для типів, чий модуль створює записи з документів (`GET /api/papers/templates/targets`; зараз — `task`).
    Вид і тип запису задаються при створенні й більше не змінюються.
  - `numberPrefix` — великі літери й цифри, до 10 знаків («ТЗ»); без нього документи без номера. `autoFreeze` — лише для `creates`.
  - `creators`: `all` (документи з шаблону створюють усі) або `staff`. `visibility` — видимість нових документів.
  - `currentVersion` — номер опублікованої версії, з якої створюються документи; `draftVersion` — номер чернетки (учасникові завжди `null`).
  - `needsUpdate` — схема запису змінилась і прив'язка поточної версії зламалась (поле пішло в архів, змінились межі…):
    потрібна нова версія. Рахується під час читання: якщо версія схеми та сама, що при публікації, перевірки немає.
- Хто бачить: admin і moderator — усі шаблони й версії; учасник — лише опубліковані, не в архіві, з `creators: all`,
  і лише їхню поточну версію. Інше — 404 `TEMPLATE_NOT_FOUND` / `TEMPLATE_VERSION_NOT_FOUND`. Змінюють лише admin і moderator.
- `GET /api/papers/templates` — за назвою. `GET /api/papers/templates/:id` — з версіями.
- `GET /api/papers/templates/targets` — `{ creates }`: типи записів, які може створювати шаблон `creates`. Лише admin і moderator.
- `POST /api/papers/templates { title, kind, target?, numberPrefix?, autoFreeze?, creators?, visibility? }` — разом із порожньою чернеткою версії 1.
  Неправильне поєднання виду, типу запису й автофіксації — 400 `TEMPLATE_KIND_INVALID`. За замовчуванням `creators: staff`, `visibility: author`.
- `PATCH /api/papers/templates/:id { title?, numberPrefix?, autoFreeze?, creators?, visibility?, archived? }` — лише передане;
  `numberPrefix: null` прибирає номер. Шаблон в архіві не показується учасникам.
- `DELETE /api/papers/templates/:id` — лише поки жодної версії не опубліковано (інакше 409 `TEMPLATE_VERSION_PUBLISHED`).
- Версія — `{ templateId, number, revision, publishedAt, publishedBy, updatedAt, body, fields, schemaVersion }`.
  `body` — документ ProseMirror, перевіряється так само, як вміст документа. `schemaVersion` — версія схеми запису, з якою версію опубліковано.
  - `GET /api/papers/templates/:id/versions/:v` — версія з вмістом.
  - `POST /api/papers/templates/:id/versions` — чернетка: наявна або нова (наступний номер), копія поточної версії. Чернетка в шаблону одна.
  - `PATCH /api/papers/templates/:id/versions/:v { revision, body?, fields? }` — лише чернетка (інакше 409 `TEMPLATE_VERSION_PUBLISHED`);
    `revision` — як у документів (інша — 409 `PAPER_CONFLICT`), `fields` — усі поля версії, по порядку. Відповідь — без `body` і `fields`.
    Тут перевіряється лише форма полів і повтор ключів: конструктор зберігає й недоналаштовані поля.
  - `GET /api/papers/templates/:id/versions/:v/fields` — поля версії (і чернетки) так, як їх заповнює документ: `{ id, title, version, fields }`,
    поле — як у документа (межі тісніші з поля запису, варіанти `enum`, `plain`); `canFill` — для всіх полів, крім `ref:*` до типів, яких не
    пов'язують. Конструктор так дає спробувати шаблон: нічого не зберігається. Лише admin і moderator.
  - `DELETE /api/papers/templates/:id/versions/:v` — відкинути чернетку.
  - `POST /api/papers/templates/:id/versions/:v/publish` — повна перевірка полів за схемою запису на цю мить і звірка тіла з полями;
    версія стає поточною й більше не змінюється.
- Поле версії — `{ key, label, type, required, fill, editable, print, binding, min, max, maxLength, maxItems, dictionary }` (до 200 полів):
  - `key` — латиницею з малої літери, до 40 знаків, унікальний у версії; значення документів зберігаються за ним.
  - `type` — тип поля зі схем записів: `text`, `richtext`, `int`, `decimal`, `date`, `datetime`, `bool`, `enum`, `color`, `ref:<тип запису>` або `list<…>`.
    `ref:<тип>` публікується лише для типів, які можна пов'язувати (див. «Зв'язки»: їх шукає пікер).
  - `fill`: `author` (автор документа) або `staff` (модератор, адмін). `editable` — можна змінити після публікації документа. `print` — показувати в друці.
  - Межі: `min`, `max` — лише `int` і `decimal` (`int` — цілі); `maxLength` — `text`, `richtext`, `list<text>`; `maxItems` — `list<…>`.
  - `dictionary` — лише `enum` і `list<enum>` без прив'язки (обов'язковий, довідник має існувати). Прив'язане поле бере значення з поля запису.
  - `binding` — ключ поля схеми `target` (`GET /api/records/:type/schema`), до кожного — не більше одного поля. `report` прив'язується до будь-якого
    поля, `creates` — лише до полів зі `create: true`, `free` — ні до чого. Тип той самий, що в поля запису; виняток — `richtext` до `text`
    (вільна зона в текстове поле: лише текст з абзацами). Межі — не ширші, ніж у поля запису. Поле в архіві не прив'язується.
    У `creates` кожне поле запису з `required` має бути прив'язане полем із `required: true`.
  Помилка — 400 `TEMPLATE_FIELD_INVALID` з `field` (ключ поля шаблону) або `binding` (ключ поля запису, якого бракує).
- Тіло й поля під час публікації: кожне поле стоїть у тілі (`field` — скільки завгодно разів, `richtext` — один раз як `fieldZone`),
  ключів, яких немає серед полів, у тілі немає, усередині зони немає полів; зона, прив'язана до текстового поля запису, починається
  простими абзацами. Помилка — 400 `TEMPLATE_FIELD_INVALID` з `field`.
- Довідник, з якого бере значення поле опублікованої версії, не видаляється (`DICTIONARY_IN_USE`).
- Аудит (`entity: paper_template`): `paper_template.created`, `paper_template.updated` (`changes`), `paper_template.deleted`,
  `paper_template.published` (`version`), `paper_template.draft_discarded` (`version`). Збереження чернетки версії не пишеться.

### Розумна лабораторія

- `GET /api/smart/entities` — дозволені пристрої зі станом: світло (`on`, `brightness` у %), датчики (`value`, `unit`, `deviceClass`),
  сцени. `:id` — це id зі списку, а не назва пристрою в HA.
- `POST /api/smart/lights/:id/state { on, brightness? }` повертає новий стан; `POST /api/smart/scenes/:id/activate`. Ліміт — 30 дій на хвилину.
- Список дозволених (admin): `status`, `discover` (пристрої HA, яких ще немає в списку), `allowlist` (додати, змінити назву, кімнату, `enabled`, прибрати).

### Розширена панель

- Лише порт 3001, admin із сесією 2FA. `overview` (метрики, контейнери, останній бекап), `logs?lines=` (до 500).
- Дії (`backup`, `restore-check`, `restart { target: api | ha }`) відповідають 202 із задачею; стан — `GET /api/admin-panel/jobs/:id`
  (`running`, `succeeded`, `failed`, до 100 рядків виводу). Одночасно — лише одна дія. Після перезапуску API клієнт має чекати й повторювати.

### Аудит

- `GET /api/audit?action=&actorId=&entity=&before=&limit=` (admin) — масив, нові спершу. `action` — точна дія (`user.updated`)
  або група з крапкою (`user.`). Наступна сторінка — `before=<id останнього запису>`, без пропусків.
  `actorId: null` — дія самого сервера (наприклад, автозакриття сеансу).

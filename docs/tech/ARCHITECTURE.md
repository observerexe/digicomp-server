# Архітектура DigiComp HUB

Як влаштована система, хто що може і як вона захищена. Для того, хто підтримує чи розвиває проєкт.
Як запустити й змінювати код — [DEVELOPMENT.md](DEVELOPMENT.md). Правила API — [API.md](API.md). Сервер — [OPERATIONS.md](OPERATIONS.md).

## Загальна схема

```
Телефон / браузер ──https──▶ Tailscale Funnel ──▶ API 127.0.0.1:3000  (застосунок + /api)
Адмін у tailnet ───https──▶ tailscale serve :9443 ──▶ API 127.0.0.1:3001  (розширена панель)

API (NestJS, контейнер) ──▶ PostgreSQL 17 (контейнер, том db_data)
                        ──▶ файли (том files_data: документи, аватари, фото, матеріали)
                        ──▶ Home Assistant (host.docker.internal:8123, REST, токен)
                        ──▶ агент сервера (unix-сокет /run/digicomp-agent/agent.sock, токен)
```

- **Один процес, один домен.** NestJS віддає і API (лише під `/api`), і зібраний фронт (будь-яка інша адреса), і `/health`.
  Тому cookie-вхід, CSRF і CSP працюють без CORS.
- **Сервер:** Ubuntu Server, Docker Compose (`db`, `api`); Home Assistant — окремий контейнер з `network_mode: host`.
  Ззовні доступний лише порт 3000 через Funnel. Порт 3001 (панель) — лише з tailnet.
- **Агент** (`ops/agent/digicomp_agent.py`, systemd) — єдиний, хто торкається docker і скриптів на сервері. API не має shell і docker socket.

### Фронт

- `src/api/client.ts` — клієнт `openapi-fetch`: завжди шле `X-DC-Client: web`, на 401 один раз оновлює сесію для всіх паралельних запитів.
- `src/auth/` — поточний користувач, вхід з 2FA, вихід. Що показувати, вирішують `permissions` з `/api/auth/me`; остаточно перевіряє сервер.
- `src/errors/messages.ts` — текст для кожного `errorCode`. Тест падає, якщо для коду з бекенду немає тексту.
- `src/layout/nav.ts` — меню: нижня панель на телефоні, бічне меню від 900 px, розділ «Керування» за правами.
- `src/pages/<розділ>/` — сторінки; `src/components/` — спільні (`Board`, `DropZone`, `ui`).
- Стилі — CSS-модулі; `src/styles/tokens.css` генерується з `docs/design/tokens.json`. Теми: системна, світла, темна.
- PWA: service worker кешує лише оболонку; відповіді API не кешуються ніколи.

## Ролі та права

Ролі: `admin`, `moderator`, `member`. Посада й спеціальність лише описують людину і на права не впливають.

| Дія | admin | moderator | member |
| --- | --- | --- | --- |
| Розширена панель (метрики, логи, бекап, перезапуск) | так | ні | ні |
| Журнал усіх дій (аудит), Swagger | так | ні | ні |
| Видати або забрати роль admin | так | ні | ні |
| Скинути пароль чи 2FA іншому | так | ні | ні |
| Змінити ім'я, email, біо іншого; видалити чужий аватар | так | ні | ні |
| Понизити чи заблокувати модератора | так | ні | ні |
| Створити учасника з паролем | так | так | ні |
| Заблокувати учасника | так | лише member | ні |
| Підвищити member до moderator | так | так | ні |
| Змінити посаду й спеціальність іншого | так | лише member | ні |
| Змінити своє біо, аватар, пароль, 2FA | так | так | так |
| Нарахувати бали, видати попередження, штраф, догану | так | так, не собі | ні |
| Зняти такий запис | так | лише виданий собою, з причиною | ні |
| Створити й редагувати ТЗ, проєкт | так | так | ні |
| Взяти ТЗ, почати, здати на перевірку | так | так | так |
| Прийняти ТЗ (нарахування балів) або повернути | так | так, не своє | ні |
| Оновити етап і прогрес проєкту | так | так | якщо учасник проєкту |
| Документи, обладнання, довідник складу: керувати | так | так | лише перегляд |
| Видати допуск до обладнання | так | так | ні |
| Склад: взяти або поповнити | так | так | так |
| Сеанс роботи з обладнанням | так | так (без допуску) | з допуском |
| Почати сеанс у чужий заброньований слот | так | ні | ні |
| Завершити чужий сеанс | так | так, з причиною | ні |
| Бронювання | так | так, скасовує будь-яке з причиною | своє, з допуском |
| Звіт про несправність | так | так, закриває | створити, фото до свого |
| Журнал обладнання: усі сеанси, CSV, друк | так | так | лише свої |
| Розумні пристрої: перегляд / керування / список дозволених | так / так / так | так / так / ні | так / ні / ні |

**Правила проти підстав**

- Пароль скидає лише адмін: інакше модератор міг би увійти від чужого імені.
- Модератор діє лише над `member`, ніколи над собою, іншим модератором чи адміном. Виняток — бали й дисципліна: їх модератор видає будь-кому, крім себе.
- Модератор не приймає ТЗ, де сам виконавець. Адмін не обмежений нічим.
- Записи не видаляються, а знімаються з причиною. Книга балів лише доповнюється. Кожна дія модератора чи адміна над іншим пишеться в аудит.
- Адмін завжди є хоча б один: понизити чи заблокувати останнього не можна (`LAST_ADMIN`).

**Де це в коді**

- `api/src/auth/policy.ts` — єдине джерело: `ROLES` (яка роль може взагалі пробувати дію) і `REFINE` (правила, що залежать від цілі:
  над ким, чий запис, чи учасник ТЗ, чи є допуск). Контролери перевіряють через `@Can(Action.X)`, сервіси — через `assertCan`.
- Тест `policy-coverage.spec.ts` не дає додати маршрут без правила; `policy.spec.ts` і `test/permissions.e2e-spec.ts` перевіряють кожен рядок матриці.
- Фронт отримує список дозволених дій у `permissions` з `/api/auth/me`; кнопки над конкретною людиною вирішує `web/src/pages/panel/userRights.ts`.

## Безпека

- **Паролі** — argon2. Пароль від 8 символів. Після зміни чи скидання пароля закриваються всі сесії людини.
- **Токени.** Доступ — JWT на 1 годину. Refresh — на 30 днів, одноразовий: у відповіді приходить новий. Повторне використання старого
  закриває всі сесії цього входу. Блокування людини діє одразу.
- **Веб-вхід через cookie.** З заголовком `X-DC-Client: web` вхід ставить HttpOnly-cookie `dc_at` (1 год) і `dc_rt` (30 днів, шлях `/api/auth`),
  `SameSite=Strict`, `Secure` при `COOKIE_SECURE=true`. Токени не потрапляють у JavaScript.
- **CSRF.** Запити, що змінюють дані за cookie, мусять мати `X-DC-Client: web`, а `Origin` (якщо є) — збігатися з адресою сервера. Інакше 403 `CSRF`.
- **Заголовки.** CSP на кожній відповіді без вбудованих скриптів і стилів і без зовнішніх ресурсів; `X-Frame-Options: DENY`, `nosniff`,
  `Referrer-Policy: same-origin`, камера дозволена лише своєму сайту (сканер QR). API — `no-store`.
- **Ліміти запитів (за хвилину).** 300 на авторизованого користувача (за токеном, не за IP), 10 спроб входу на пошту, 20 refresh/logout на токен,
  5 на `setup` і `2fa/verify`, 30 дій зі світлом і сценами. Без токена рахується за IP. `X-Forwarded-For` не довіряється без `TRUST_PROXY`.
- **2FA (TOTP).** Секрет зашифровано ключем `TOTP_KEY`. Кожен код приймається раз, запасні коди одноразові (у базі хеші),
  10 помилок поспіль — блок на 15 хвилин. Обов'язкова для розширеної панелі.
- **Розширена панель** — лише на порту 3001 (на 3000 її маршрути дають 404), лише admin і лише в сесії, де вхід був з кодом 2FA.
  Агент виконує фіксований список команд; бази, видалення й довільних команд у ньому немає.
- **Файли** перевіряються за вмістом, не за розширенням; дозволені pdf, png, jpg, webp, docx, xlsx, pptx, txt, md, csv.
  Віддаються лише авторизованим. PDF для перегляду (`inline=1`) можна вбудувати лише в сторінки застосунку.
- **Home Assistant** — лише через список дозволених пристроїв і лише `light`, `sensor`, `binary_sensor`, `scene`.
  Розетки й вимикачі (`switch.*`) додати неможливо, щоб застосунок не міг дистанційно вмикати паяльники, нагрівачі чи 3D-принтери.
- **Аудит** — кожна зміна даних і кожна дія над іншим учасником пишеться в `audit_log` (хто, що, над чим, деталі). Перегляд — `/admin/audit`.

## Дані

- **PostgreSQL 17**, схема лише через міграції (`synchronize` вимкнено), міграції застосовуються при старті API і не втрачають наявні дані.
- **Файли** — у томі `files_data` (`STORAGE_DIR`), у базі лише метадані.
- **Бали** — книга обліку (`points_ledger`): записи не змінюються, зняття додає компенсаційний запис. Баланс — сума.
- **Час** — у базі UTC; дні, місяці рейтингу, дедлайни й журнал рахуються за київським часом.
- **Бекап** — щодня о 03:30 база й файли (і конфігурація HA), зберігаються 14 останніх. Див. [OPERATIONS.md](OPERATIONS.md).

## Прийняті рішення

- **Поділ балів за ТЗ.** Порівну між виконавцями, остача — по балу тим, хто взяв ТЗ раніше (10 на трьох: 4, 3, 3). Бали за ТЗ остаточні.
- **Статуси ТЗ:** Вільне → В черзі → В роботі → На перевірці → Виконано; з перевірки можна повернути в роботу з коментарем.
- **Етапи проєкту:** Ідея → Планування → Виконання → Перевірка → Завершено; архів — окрема дія. Проєкти й ТЗ не пов'язані.
- **Забутий сеанс** закривається сам через 12 годин (`SESSION_AUTO_CLOSE_HOURS`) з позначкою «закрито автоматично».
- **Дисципліна** не має терміну дії: запис знімається вручну з причиною; знятий штраф повертає бали.
- **Акаунти** створюють модератор чи адмін з паролем; самостійної реєстрації немає. Перший адмін — через `POST /api/auth/setup`.

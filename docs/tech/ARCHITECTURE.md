# Архітектура DigiComp HUB

Як влаштована система, хто що може і як вона захищена. Для того, хто підтримує чи розвиває проєкт.
Як запустити й змінювати код — [DEVELOPMENT.md](DEVELOPMENT.md). Правила API — [API.md](API.md). Сервер — [OPERATIONS.md](OPERATIONS.md).

## Загальна схема

```
Телефон / браузер ──https──▶ Tailscale Funnel ──▶ API 127.0.0.1:3000  (застосунок + /api)
Адмін у tailnet ───https──▶ tailscale serve :9443 ──▶ API 127.0.0.1:3001  (розширена панель)

API (NestJS, контейнер) ──▶ PostgreSQL 17 (контейнер, том db_data)
                        ──▶ файли (том files_data: документи, аватари, фото, матеріали, зображення документів)
                        ──▶ Home Assistant (host.docker.internal:8123, REST, токен)
                        ──▶ агент сервера (unix-сокет /run/digicomp-agent/agent.sock, токен)
```

- **Один процес, один домен.** NestJS віддає і API (лише під `/api`), і зібраний фронт (будь-яка інша адреса), і `/health`.
  Тому cookie-вхід, CSRF і CSP працюють без CORS.
- **Сервер:** Ubuntu Server, Docker Compose (`db`, `api`); Home Assistant — окремий контейнер з `network_mode: host`.
  Ззовні доступний лише порт 3000 через Funnel. Порт 3001 (панель) — лише з tailnet.
- **Агент** (`ops/agent/digicomp_agent.py`, systemd) — єдиний, хто торкається docker і скриптів на сервері. API не має shell і docker socket.

### Фронт

- `src/api/client.ts` — клієнт `openapi-fetch`: завжди шле `X-DC-Client: web`, на 401 один раз оновлює сесію для всіх паралельних запитів.
- `src/auth/` — поточний користувач, вхід з 2FA, вихід. Що показувати, вирішують `permissions` з `/api/auth/me`; остаточно перевіряє сервер.
- `src/errors/messages.ts` — текст для кожного `errorCode`. Тест падає, якщо для коду з бекенду немає тексту.
- `src/layout/nav.ts` — меню: нижня панель на телефоні, бічне меню від 900 px, розділ «Керування» за правами.
- `src/pages/<розділ>/` — сторінки; `src/components/` — спільні (`Board`, `DropZone`, `ui`).
- Стилі — CSS-модулі; `src/styles/tokens.css` генерується з `docs/design/tokens.json`. Теми: системна, світла, темна.
  Розмір шрифту — змінні `--fs-<px на комп'ютері>`, вужче 900 px вони менші (`fontPhone`); поля введення на телефоні — не менше 16 px.
  Вибір з кількох варіантів — `components/ChoiceButton.tsx`: на телефоні меню стає панеллю внизу екрана.
- PWA: service worker кешує лише оболонку; відповіді API не кешуються ніколи.
  **Оновлення** (`lib/appUpdate.ts`, реєструє service worker сам — `injectRegister: false`): нова збірка бере керування одразу
  (`skipWaiting`, `clientsClaim`; без них вона чекала б, доки закриють усі вкладки, а застосунок на телефоні не закривають).
  Відкрита сторінка перевіряє оновлення, коли знову стає видимою, раз на 30 хв і з появою мережі; якщо нова збірка взяла
  керування, сторінка перезавантажується, лише коли це нікому не заважає: її сховали чи людина перейшла на іншу сторінку
  (`router.subscribe` у `main.tsx`). Стара сторінка, якій бракує файлу коду (`vite:preloadError`), перезавантажується раз
  (не частіше ніж раз на 10 с — `sessionStorage`). `index.html`, `sw.js` і маніфест сервер віддає з `no-cache`.
- Чернетки на пристрої (`lib/localDrafts.ts`, IndexedDB `digicomp`, сховище `drafts`): зміни чернетки документа чи версії шаблону,
  яких сервер ще не отримав, — один запис на чернетку (ключ «користувач|вид|id»: `revision`, з якою вони йдуть, і незбережені частини,
  разом із тими, що в дорозі). `useAutosave` пише запис з кожною зміною і прибирає, щойно сервер прийняв усе; конфлікт і відмова сервера
  запис лишають. Чернетки, яких не тримає відкритий редактор, `sendDrafts` надсилає по одній після входу й на подію `online`
  (`AuthProvider`): прийняте — прибирає, решту лишає до відкриття. Редактор спершу забирає свій запис (`claimDraft` чекає, доки фон
  досилає саме його, і далі фон його не чіпає), лише потім читає документ; запис проти відповіді сервера (`useLocalDraft`, `verdictOf`
  на сторінці): та сама `revision` і досі чернетка — зміни відновлюються в редакторі й надсилаються одразу; сервер уже має саме їх
  (порівняння JSON без порядку ключів) — запис прибирається; інакше — екран вибору замість редактора: «Зберегти мої зміни як копію»
  (`POST /papers/:id/copy`; для шаблону копії немає) або «Відкинути мої зміни». Документа немає (403/404) — запис прибирається.
  Вихід прибирає всі записи; вхід — записи інших людей; сеанс, що закінчився сам, їх лишає. Без IndexedDB усе працює з пам'яті, як раніше.
- **Редактор** (`/editor`, `src/pages/editor/`, ядро — `src/editor/`): список «Мої» / «Усі» / «Шаблони» (вкладка в адресі, `?tab=`;
  «Шаблони» — з правом `paper_templates.manage`), сторінка документа й конструктор шаблону.
  Сторінка документа з TipTap вантажиться ліниво (окремий чанк), список — ні. Документ (`/editor/:id`) займає все вікно — маршрут
  поза `AppShell`, без бічного меню й нижньої панелі; повернення — стрілкою «Назад» і посиланням у шляху.
  Вікно: верхній рядок (шлях, назва, стан, «Збережено о…»), стрічка `editor/Ribbon.tsx` («Головна» і «Вставка»; кнопки викликають
  команди з `editor/extensions.ts` і показують стан у місці курсора через `useEditorState`), аркуш із лінійкою `editor/Ruler.tsx`
  (SVG у міліметрах аркуша) і рядок стану `editor/StatusBar.tsx`. Сторінки рахує `editor/usePageStats.ts` приблизно: за висотою
  частин між розривами на екрані (257 мм тексту на аркуш); точний поділ — у друці. Масштаб — класи з CSS `zoom` (кроки 50–200 %),
  зберігається в `localStorage` (`editor.zoom`). Шрифт аркуша — стек `'Times New Roman', 'Liberation Serif', serif`;
  Liberation Serif 2.1.5 (SIL OFL 1.1, метрики Times New Roman) лежить у `web/public/fonts/` повністю, без обрізання
  (обрізаний шрифт за OFL довелося б перейменувати); `@font-face` — у `shared/editor-schema/paper.css`, тож браузер просить шрифт лише для аркуша
  (service worker кешує його разом з іншими шрифтами). TipTap складено так, щоб його схема точно
  збігалася зі спільним описом `shared/editor-schema/` (тест `editor/schema.test.ts` порівнює вузли, позначки, атрибути й дозволених дітей).
  Форматування — лише класи з фіксованого набору (`fs-*` розмір, `tc-*` колір, `ff-*` шрифт, `ta-*` вирівнювання, `in-*` відступ),
  правила — у `shared/editor-schema/paper.css` (вигляд аркуша, спільний з друком); атрибута `style` у вмісті немає, бо CSP його блокує.
  Власний `<style>` TipTap теж заблоковано, тому `injectCSS: false`, а потрібні правила ProseMirror лежать в `editor/format.css`.
  Аркуш завжди білий: кольори тексту — `--sheet-*` (світлі значення палітри в обох темах).
  «Попередній перегляд» у верхньому рядку зберігає незбережені зміни й відкриває сторінку друку (`/api/papers/:id/print`) у новій вкладці;
  вкладка відкривається одразу, а адреса ставиться після збереження, інакше браузер заблокував би її як спливне вікно. Автозбереження (`editor/useAutosave.ts`) — через 1,5 с після останньої зміни,
  один `PATCH` за раз з останньою `revision`; на 409 зупиняється й пропонує «Відкрити останню версію» або «Зберегти мою як копію».
  Без зв'язку повторює через 10 с і одразу на `online`; поки зміни лежать на пристрої — «Збережено на цьому пристрої, надішлемо пізніше»,
  і закриття вкладки не перепитує (перепитує, лише коли зміни ще не записано й на пристрій).
  Поле `ref:*` у панелі «Поля» — пошук із випадним списком (`editor/fieldTypes/ref.tsx`, `GET /links/candidates`); «@» у тексті
  (`editor/mention.ts`, `@tiptap/suggestion`) відкриває список записів п'яти типів (`editor/MentionMenu.tsx`) і вставляє вузол `mention`
  лише з типом і id. Назви записів сторінка документа тримає в одній мапі (`refs` з відповіді плюс вибране тут; `editor/records.tsx`):
  з неї читають панель, поля на аркуші й посилання «@». Усе заповнення (значення, тексти зон, активне поле, мапа записів, «@», вигляд
  полів на аркуші) — у хуках `editor/useFill.ts` (`useFill` до редактора, `useFillSheet` після): ними користуються і сторінка документа,
  і спроба шаблону в конструкторі. У документі з шаблону Tab і Shift+Tab переходять між полями, які людина заповнює
  (`nextField` у `editor/fields.ts`): зона — курсор у неї, поле в рядку — його введення в панелі; у списку й таблиці Tab лишається своїм.
  Автозбереження спільне для документа й шаблону: `useAutosave` отримує функцію збереження (`PATCH` документа чи версії шаблону);
  `flush` зберігає одразу й каже, чи все вже на сервері (перед друком, спробою й публікацією).
  **Телефон** (вужче за 900 px, `lib/useMediaQuery.ts`): замість стрічки — `MiniRibbon` (один рядок: скасувати, повторити, Ж, К, П, списки;
  ті самі команди й те саме блокування поза зонами), дії верхнього рядка — під «⋯», «Збережено о…» — унизу. Документ із шаблону має
  перемикач «Форма / Сторінка» (спершу «Форма»; редактор при цьому не перестворюється, а ховається). «Форма» (`editor/PaperForm.tsx`) — ті самі
  групи полів, що й панель «Поля» (`FieldGroups` у `editor/FieldsPanel.tsx`), на весь екран, унизу — скільки обов'язкових заповнено. Зона
  `plain` пишеться у формі полем для тексту: `setZoneText` (`editor/fields.ts`) замінює вміст зони абзацами — рядок на абзац — тією самою
  транзакцією, що й друк на аркуші (фільтр зон діє й тут); зона з форматуванням показує початок тексту, «Писати на сторінці» відкриває
  «Сторінку» з курсором у зоні: форматування й «@» живуть лише на аркуші. Клік чи Tab до поля на «Сторінці» відкриває «Форму» з цим полем
  (`showControls` у `useFill`).
- **Розваги** (`/fun`, `src/pages/fun/`): список ігор; «Бункер» (`/fun/bunker`, вкладки в адресі `?tab=`: кімнати, «Карти і паки»
  з `?pack=`, правила). Кімната (`/fun/bunker/:id`, `RoomPage.tsx`) займає все вікно, як документ редактора: лобі, гра, фінал.
  Сервер нічого не надсилає сам, тож відкрита кімната питає `GET /api/bunker/rooms/:id` раз на 2 с, список кімнат — раз на 5 с
  (`queries.ts`); відповідь на дію одразу стає станом сторінки. Таймер ходу рахує від часу сервера (`now` у відповіді).
  Вужче за 900 px гра — вкладки «Мої карти / Гравці / Бункер», на комп'ютері — усе поруч. Назви видів карт, їхні кольори (з палітри,
  як пункти довідника) і тексти хроніки — `pages/fun/bunker/labels.ts`.
- **Конструктор шаблону** (`/editor/templates/:id`, `pages/editor/TemplatePage.tsx`, з правом `paper_templates.manage`) — так само на все вікно
  й ліниво. Якщо в шаблону є чернетка (або ще нічого не опубліковано) — відкриває її (`POST /papers/templates/:id/versions` повертає наявну
  або робить нову) і зберігає автоматично (`PATCH …/versions/:v` з `revision`; 409 — «Відкрити останню версію»). Без чернетки показує
  поточну версію лише для читання (рамки без підказки внизу й без «/», з панелі — лише «Шаблон»); «Змінити» робить чернетку з неї,
  тож чернетка не з'являється від самого перегляду. Вужче за 900 px не відкривається (`lib/useMediaQuery.ts`).
  Блок — вузол верхнього рівня тіла. Реєстр блоків `editor/blocks/` (файл на блок, як `fieldTypes/`): група (текст, поля, дані застосунку,
  авто — номер, дата, автор, авто-таблиці; структура — шапка, «Затверджую», підписи, колонтитул),
  назва, іконка; текстовий блок — що вставляє і які вузли ним є, блок поля — тип поля, префікс ключа, варіанти типу («Ціле» / «Дробове»,
  «Один» / «Кілька»). Блоки даних застосунку — лише `ref:<тип>`: редактор не знає, що це за записи. На аркуші (`editor/builder.ts`) кожен
  блок у рамці з міткою (`data-label`, колір групи), поле — `{Підпис}` або `{key}`; блок ставиться кліком у палітрі (біля курсора),
  перетягуванням (`application/x-paper-block`) чи «/» (`@tiptap/suggestion`, `editor/BlockMenu.tsx`). Блок верхнього рівня
  переставляє `moveBlock(editor, index, before)` — у проміжок перед блоком `before`, з полями й зонами, виділення в ньому їде разом:
  «⠿» (`blockHandle`, вид плагіна: кнопка й лінія проміжку — поруч з аркушем, у його обгортці, за `offsetTop`/`offsetLeft`, тож
  масштаб аркуша, CSS `zoom`, їх не зсуває; перетягування — pointer events із захопленням, не DnD ProseMirror, щоб не змішувалось
  із палітрою й `dropcursor`; Esc скасовує), «Вгору» / «Вниз» у «Властивостях» і Alt+↑ / Alt+↓. Рамка блока (`.paper-block`, від'ємні
  поля) не зсуває того, що друк ставить полями: «Затверджую» праворуч і відступи абзаців — окремими правилами у `format.css`. У шаблоні з записом палітра й «/»
  починаються з групи «Поля запису «<тип>»» (`editor/blocks/schema.ts`): блок на кожне поле схеми, до якого можна прив'язатися
  (`creates` — поля зі `create`, потім авто-поля; `report` — спершу сам запис, поле `ref:<тип>`, яке вибирає людина, потім усі поля — авто);
  він ставить поле одразу прив'язаним — тип і назва поля запису, ключ — його ключ, поки той вільний,
  обов'язковість — як у запису (для `creates`), довгий текст (понад 500 знаків, не авто) — вільна зона. Поле запису звіту
  (`reportRecordOf` у `editor/template.ts`) у «Властивостях» — пояснення замість зв'язку й перемикачів: воно завжди обов'язкове й незмінне. Поле запису, вже прив'язане на аркуші,
  удруге не пропонується. Поле стає в текст; у вільній зоні — після
  зони: поле в зоні й зона двічі відкидаються фільтром транзакцій. Вставлене з буфера тримає лише поля цього шаблону, зону, що вже є, —
  як текст. Поля версії — ті, що на аркуші, у порядку аркуша (`editor/template.ts`; учасник, що підписує колонку підписів, — теж поле;
  перейменування й видалення поля змінюють і підписи); налаштування прибраних полів сторінка пам'ятає, тож
  «Скасувати» повертає поле з ними. Панель (`editor/BuilderPanel.tsx`): «Блоки» — палітра, «Властивості» — поле (ключ, підпис, вид, зв'язок
  із полем запису того самого типу, межі, довідник, хто заповнює, перемикачі) або текстовий блок (підписи — підпис і хто підписує
  кожну колонку, колонтитул — текст, авто-таблиця — «Звідки» й підпис її поля; `setBlockAttrs`), «Шаблон» (`pages/editor/TemplateSettings.tsx`) —
  налаштування всього шаблону, що діють одразу (`PATCH /papers/templates/:id`): назва, префікс номера, хто створює й бачить документи, автофіксація,
  версії з кількістю документів, «Відкинути чернетку», архів або видалення неопублікованого. Зміна виду поля прибирає те, що йому не пасує,
  і зв'язок. «Опублікувати vN» дозберігає чернетку й публікує; відмова з `field` виділяє поле й відкриває «Властивості», з `binding` — каже,
  якого поля запису бракує. Режим «Документ» — спроба (`pages/editor/TemplateTrial.tsx`): чернетка дозберігається, сервер віддає поля, як їх
  заповнює документ (`GET …/versions/:v/fields`), і окремий редактор з тілом версії заповнюється, як документ (панель «Поля», Tab, пікери, «@»);
  значення живуть лише на сторінці, документ не створюється. Аркуш конструктора тим часом лишається змонтованим (прихований), тож історія
  змін не губиться. Сенс полів сервер перевіряє під час публікації.

## Ролі та права

Ролі: `admin`, `moderator`, `member` — команда, і `guest` — гість. Посада й спеціальність лише описують людину і на права не впливають.

**Гість** — не член команди. Він має лише явно перелічені дії (`EVERYONE` або `G` у `policy.ts`; решта ролей — `ALL`, тобто команда):
«Розваги» (`bunker.play`), рейтинг (`rating.read`), огляд ТЗ (`tasks.overview`, `GET /tasks/overview`) і проєктів (`projects.overview`,
`GET /projects/overview`) — назва, статус чи етап, хто виконує, без опису, файлів, коментарів, документів та історії; свій профіль (біо,
аватар, колір, пароль, 2FA). Нова дія гостю сама не відкривається — це перевіряє тест `policy.spec.ts`. Гостя немає в команді: у списку людей
(`GET /users` без `guests=true`, а цей параметр — лише для admin і moderator), рейтингу, виборі людей (учасники проєкту, бали, стягнення,
допуски, підписант, посилання на людину в документах). Створюють гостя admin і moderator («Новий учасник» → роль «Гість»); модератор
діє над гостем, як над `member` (блокує, переводить у `member` і назад). На фронті гість має свою розкладку (`isGuest`, `layout/nav.ts`:
`GUEST` — бічне меню й нижня панель без QR), «Головна» веде в «Розваги», сторінки команди за `TeamOnly` (`auth/RequireAuth.tsx`)
показують «Немає доступу», а `/tasks` і `/projects` — огляд (`TasksOverviewPage`, `ProjectsOverviewPage`). Це лише вигляд: що можна, вирішує API.

**Правила проти підстав**

- Пароль скидає лише адмін: інакше модератор міг би увійти від чужого імені.
- Модератор діє лише над `member` і `guest`, ніколи над собою, іншим модератором чи адміном. Виняток — бали й дисципліна: їх модератор видає будь-кому, крім себе.
- Модератор не приймає ТЗ, де сам виконавець. Адмін не обмежений нічим.
- Записи не видаляються, а знімаються з причиною. Книга балів лише доповнюється. Кожна дія модератора чи адміна над іншим пишеться в аудит.
- Адмін завжди є хоча б один: понизити чи заблокувати останнього не можна (`LAST_ADMIN`).

**Де це в коді**

- `api/src/auth/policy.ts` — єдине джерело: `ROLES` (яка роль може взагалі пробувати дію) і `REFINE` (правила, що залежать від цілі:
  над ким, чий запис, чи учасник ТЗ, чи є допуск). Контролери перевіряють через `@Can(Action.X)`, сервіси — через `assertCan`.
- Тест `policy-coverage.spec.ts` не дає додати маршрут без правила; `policy.spec.ts` і `test/permissions.e2e-spec.ts` перевіряють кожен рядок матриці.
- Фронт отримує список дозволених дій у `permissions` з `/api/auth/me`; кнопки над конкретною людиною вирішує `web/src/pages/panel/userRights.ts`.

## Безпека

- **Паролі** — argon2. Пароль від 8 символів. Після зміни чи скидання пароля закриваються всі refresh-сесії людини; уже виданий
  доступ (JWT) діє до свого кінця, до години. Вхід з невідомою поштою теж перевіряє хеш, щоб час відповіді не показував, чи є така пошта.
- **Токени.** Доступ — JWT на 1 годину. Refresh — на 30 днів, одноразовий: у відповіді приходить новий. Повторне використання старого
  закриває всі сесії цього входу. Блокування людини діє одразу.
- **Веб-вхід через cookie.** З заголовком `X-DC-Client: web` вхід ставить HttpOnly-cookie `dc_at` (1 год) і `dc_rt` (30 днів, шлях `/api/auth`),
  `SameSite=Strict`, `Secure` при `COOKIE_SECURE=true`. Токени не потрапляють у JavaScript.
- **CSRF.** Запити, що змінюють дані за cookie, мусять мати `X-DC-Client: web`, а `Origin` (якщо є) — збігатися з адресою сервера. Інакше 403 `CSRF`.
  Без перевірки — лише запити без cookie або з `Authorization: Bearer …` (тоді токен береться із заголовка, не з cookie).
- **Заголовки.** CSP на кожній відповіді без вбудованих скриптів і стилів і без зовнішніх ресурсів; `X-Frame-Options: DENY`, `nosniff`,
  `Referrer-Policy: same-origin`, камера дозволена лише своєму сайту (сканер QR). API — `no-store`.
  Сторінки для друку (журнал обладнання, документ редактора) мають свій CSP: `default-src 'none'`, єдиний вбудований стиль дозволено
  його хешем, документу редактора — ще шрифти й зображення з `'self'`; скриптів немає.
- **Ліміти запитів (за хвилину).** 300 на авторизованого користувача (за токеном, не за IP), 10 спроб входу на пошту, 20 refresh/logout на токен,
  5 на `setup` і `2fa/verify`, 30 дій зі світлом і сценами. Без токена рахується за IP. `X-Forwarded-For` не довіряється без `TRUST_PROXY`.
- **2FA (TOTP).** Секрет зашифровано ключем `TOTP_KEY`. Кожен код приймається раз, запасні коди одноразові (у базі хеші),
  10 помилок поспіль — блок на 15 хвилин. Обов'язкова для розширеної панелі.
- **Розширена панель** — лише на порту 3001 (на 3000 її маршрути дають 404), лише admin і лише в сесії, де вхід був з кодом 2FA.
  Агент виконує фіксований список команд; бази, видалення й довільних команд у ньому немає.
- **Файли** перевіряються за вмістом, не за розширенням; дозволені pdf, png, jpg, webp, docx, xlsx, pptx, txt, md, csv
  (зображення документів редактора — лише png і jpg).
  Віддаються лише авторизованим. PDF для перегляду (`inline=1`) можна вбудувати лише в сторінки застосунку.
- **Home Assistant** — лише через список дозволених пристроїв і лише `light`, `sensor`, `binary_sensor`, `scene`.
  Розетки й вимикачі (`switch.*`) додати неможливо, щоб застосунок не міг дистанційно вмикати паяльники, нагрівачі чи 3D-принтери.
- **Аудит** — кожна зміна даних і кожна дія над іншим учасником пишеться в `audit_log` (хто, що, над чим, деталі); дії — лише зі списку `api/src/audit/actions.ts`. Перегляд — `/admin/audit`.

## Дані

- **PostgreSQL 17**, схема лише через міграції (`synchronize` вимкнено), міграції застосовуються при старті API і не втрачають наявні дані.
- **Файли** — у томі `files_data` (`STORAGE_DIR`), у базі лише метадані.
- **Довідники** — `dictionaries` і `dictionary_items`. Записи зберігають **ключ** пункту, а не назву. Ключ сервер створює з назви
  транслітерацією один раз (`Тип ТЗ` → `typ_tz`), тому назву можна змінювати вільно. Колір пункту — назва з палітри `tokens.json`.
  Модуль, що зберігає ключі пунктів, реєструє в `DictionaryUsageRegistry` перевірку: пункт у вжитку не видаляється
  (`DICTIONARY_ITEM_IN_USE`) — його переносять в архів; довідник, на який спирається модуль, не видаляється взагалі.
  Новий пункт у запис — лише неархівний (`assertDictionaryItem`); архівний лишається, поки його не змінили.
  Зараз так зберігають категорії: `places.category` (`place_category`), `documents.category` (`document_category`),
  `inventory_items.category` (`inventory_category`). Ці довідники створює міграція з наявних значень.
  Довідник `task_type` «Тип технічного завдання» (Програмування, Дизайн, SMM, Відео, 3D-друк, Інше — з кольорами) і поле ТЗ
  `type` «Тип» створює міграція `TaskTypes` (див. «Додаткові поля»).
- **Схеми записів** — опис полів кожного типу записів (тип, межі, чи можна задати при створенні й змінити) лежить у модулі,
  що володіє записом: `api/src/<модуль>/<тип>.schema.ts`; реєстр — `api/src/records/records.registry.ts`. Ключі типів ті самі,
  що `entity` в аудиті (виняток — `inventory_writeoff`, «Списання зі складу»: це рух складу, аудит пише його як `inventory_item`).
  Редактор документів працює лише зі схемами й нічого не знає про конкретні розділи.
  Тест `records/schemas.spec.ts` порівнює схему з DTO (поля, обов'язковість, межі, значення) і з колонками сутності:
  змінили DTO чи таблицю — оновіть схему. Поле `computed` модуль рахує сам; таке поле може задаватися при створенні
  (кількість списання — модуль пише її рухом з мінусом), але не змінюється. Секрети (пароль, 2FA) у схеми не потрапляють.
- **Додаткові поля** — описові поля, які admin і moderator додають без коду: визначення в `record_field_defs` (тип, назва, ключ, межі, довідник,
  порядок, архів), значення — у колонці `extra jsonb` запису. Тип записів стає доповнюваним, коли його схема має `extensible: true`,
  сутність — колонку `extra`, а DTO — поле `extra` (це перевіряє `schemas.spec.ts`); зараз так лише `task`.
  Модуль перевіряє `extra` через `RecordFieldsService.applyExtra` у своїй транзакції. Логіка (статус, бали, термін) лишається
  справжніми колонками; перенесення поля з `extra` у колонку зберігає ключ, тож шаблони не ламаються. Поле зі значеннями
  не видаляється, а йде в архів. Модуль `records` реєструє вжиток довідників: довідник поля й пункти в `extra` не видаляються.
  На фронті поля — у `web/src/lib/fields.ts` (запит, перетворення значень форми, перевірка) і `web/src/components/ExtraFields.tsx`
  (віджети форми й показ значень); керування — `/panel/fields/:type`. На дошці ТЗ перше неархівне поле `enum` фарбує всю
  картку в колір свого пункту й дає позначку з назвою, а кожне неархівне поле `enum` чи `list<enum>` — фільтр (на клієнті, за завантаженими ТЗ).
  На кожній установці є поле ТЗ `type` «Тип» — `enum` з довідника `task_type`, обов'язкове (міграція `TaskTypes`; ТЗ, що вже були,
  отримали «Інше»). Шаблони «Технічне завдання» й «Коротке ТЗ» мають його з версії 2 (міграція `TaskTypeTemplates`, її, як і інші
  міграції початкових шаблонів, знову запускає `POST /auth/setup`); шаблон, що створює ТЗ без цього поля, потребує нової версії.
  Поле — звичайне додаткове: назву, обов'язковість, порядок і архів змінюють у «Налаштуваннях полів», типи — у «Довідниках».
- **Зв'язки** — `record_links` (`from_type`, `from_id`, `to_type`, `to_id`, `role`, хто й коли). Типи — ключі схем записів;
  зовнішніх ключів до записів немає, тому модуль, що видаляє запис, прибирає його зв'язки (`removeLinksOf`; зараз — ТЗ і чернетка документа).
  Пара з однією роллю — один раз у будь-якому напрямку (унікальний індекс за впорядкованою парою). Пов'язувати можна типи,
  які модуль зареєстрував у `LinkRegistry` (`<модуль>/<тип>.links.ts`): хто редагує запис (через `policy.ts`), які записи людина бачить
  і пошук видимих записів для вибору (`search`).
  Зараз це `task`, `project`, `place`, `inventory_item`, `fault`, `document`, `user`, `paper`, `discipline_record`. Зв'язує той, хто може редагувати джерело,
  і лише видимі йому записи; від `user`, `paper` і `discipline_record` вручну не зв'язують (`checkEdit` — `FORBIDDEN`): учасників і стягнення
  згадують документи, а зв'язки документа виводяться з його вмісту. Стягнення бачать admin і moderator — усі, учасник — свої
  (назва — «Штраф −5 · Ім'я · 12.11.2026», пошук — за підставою й іменем). Несправності (`fault`) бачать усі, зв'язують admin і moderator
  (як закривають); назва — «Несправність: <обладнання>, дд.мм.рррр», закрита — архівна, `code` — код її обладнання (посилання веде на
  сторінку обладнання, `#faults`).
  у списку зв'язків людина бачить лише доступні їй записи. Документи архіву прив'язуються до обладнання й позицій складу саме так,
  фільтр Архіву (`GET /archive`) — `?linkedType=&linkedId=`, і для файлів, і для документів редактора. На фронті зв'язки показує один компонент — блок «Пов'язане» (`components/Related.tsx`)
  на сторінках ТЗ, проєкту, обладнання, позиції складу й документа архіву: групи за типом, перша — «Документи» (файли архіву й документи
  редактора разом); пов'язати чи прибрати —
  там само, за `canLink` / `canRemove` з відповіді. Пікер записів (`LinkPicker`) — і в блоці, і у формі нового документа архіву.
- **Реквізити** — `org_settings`, рівно один рядок (`id = 1`, перевірка в базі): назва закладу й групи (шапка документів),
  підписант за замовчуванням (`signer_id` → `users`, видалення учасника очищає поле) і посада під підписом — окремим текстом,
  бо посада в профілі може бути іншою. Шаблони документів не вшивають ці значення, а беруть звідси. Керування — `/panel/org`.
- **Документи редактора** — `papers`: назва, вміст (`content jsonb`, документ ProseMirror), стан, видимість, автор, `revision`.
  Кожне збереження надсилає `revision`, з якої почалася зміна; якщо документ тим часом змінили — 409 `PAPER_CONFLICT`
  (рядок блокується на час зміни). Спільного редагування наживо немає. Чернетку бачать автор, admin і moderator; опублікований документ
  з видимістю «усі учасники» — усі. Видаляється лише чернетка. Автозбереження автора в аудит не пишеться (інакше журнал заповнять
  збереження кожні кілька секунд); створення, видалення, зміна видимості й зміна чужого документа — пишуться.
  Вміст перевіряється за спільним описом `shared/editor-schema/` (`checkContent`): лише відомі вузли, позначки й значення атрибутів,
  кожен вузол — лише там, де його дозволяє схема; той самий опис будує редактор на фронті. Для `/api/papers` тіло запиту — до 1 МБ (`PAPER_BODY_LIMIT`
  у `setup-app.ts`; парсер названо окремо, бо Nest не ставить свій, якщо бачить шар `jsonParser`).
  **Друк** (`paperwork/print.ts`) — сторінка A4 за зразком журналу обладнання: HTML будує `renderContent` зі спільного опису
  (`shared/editor-schema/render.ts`, без залежностей; `@tiptap/html` не потрібен), вигляд — той самий `paper.css`, що й в редакторі,
  кольори аркуша — `SHEET_COLORS`. Тест `web/src/editor/render.test.ts` перевіряє, що рендер дає той самий HTML, що й TipTap,
  а `paperwork/print.spec.ts` — що `SHEET_COLORS` збігаються з `tokens.json`. Друк і PDF — лише зі знімка; документ без знімка
  друкується з поточного вмісту з водяним знаком («Чернетка», «Не зафіксовано», «Скасовано»: `position: fixed` повторюється на кожній сторінці).
  Шапку друк сам не додає. **Копія DOCX** (`paperwork/docx.ts`, бібліотека `docx`) будується з того самого HTML аркуша, що й друк
  (знімок або `sheetHtml`; вибір — `PaperworkService.sheetOf`, спільний для друку й DOCX), а не з JSON вмісту: так копія зафіксованого
  документа каже те саме, що знімок (і старі знімки звіту, і після зміни Реквізитів), а логіка полів, умов, повторюваних рядків і авто-таблиць
  живе лише в `render.ts`. Розбирає HTML власний маленький токенізатор (`parseSheet`): HTML аркуша — лише з `render.ts`, тож знає його теги
  й класи; незнайомий тег пропускається, його текст лишається. Відповідності: абзац — відступ першого рядка 10 мм (не в списках, таблицях,
  структурі, по центру й праворуч), заголовки — стилі Word `Heading1–3`, списки — нумерація Word (`ol` зі своїм `start`), таблиці — фіксовані
  рівні колонки з рамками й об'єднаними клітинками, авто-таблиця — 12 pt з повтором рядка-шапки, «Затверджую» — відступ на половину аркуша,
  «Блок підписів» — таблиця без рамок, порожнє поле й лінії підпису — підкреслені нерозривні пробіли, «sans» — Arial (e-Ukraine у Word
  рідко є). Між двома таблицями поспіль — тонкий абзац (Word зливає таблиці, що торкаються). DOCX — лише копія: печатки й QR немає,
  замість неї — рядок «Копія документа…» з посиланням на перевірку й SHA-256; водяний знак — словом у верхньому колонтитулі.
  **Структура аркуша** — вузли спільного опису лише на верхньому рівні: `orgHeader` (шапка),
  `approval` (гриф «Затверджую»), `signatures` (підписи: хто підписує — автор, підписант з реквізитів або учасник поля `ref:user`),
  `pageFooter` (колонтитул). У вмісті — лише вузол і його атрибути; що вони показують (реквізити, імена «Ім'я ПРІЗВИЩЕ», рік),
  дає `PaperInfo`: на сервері — `printHtml`, у редакторі — `editor/useSheet.ts` → `setSheetInfo` (`editor/structure.ts`).
  Обидва малюють той самий HTML (`structureInner` у `render.ts`). Колонтитул друкується в `@page @bottom-center`, тому стиль сторінки
  свій для кожного документа, і CSP містить хеш саме його (`printCsp`). Авто-значення `paperNumber`, `paperDate` (день публікації),
  `paperAuthor` — вбудовані вузли без атрибутів; у редакторі їх малює той самий `structure.ts`.
- **Документ із шаблону** — `papers.template_version_id` (версія, з якої його зроблено; документ лишається на ній) і `values jsonb`
  (значення полів за ключами). У вмісті поле — вузол `field` лише з ключем: значення живе у `values`, а аркуш і друк показують його.
  Вільна зона (`richtext`) — вузол `fieldZone` з текстом автора всередині вмісту. Поза зонами текст заблокований: на фронті —
  фільтр транзакцій (`web/src/editor/fields.ts`), на сервері — звірка з тілом версії (`matchesBody` у `shared/editor-schema/fields.ts`:
  обидва документи зводяться до однієї форми — атрибути за замовчуванням, порядок позначок, злитий текст — і порівнюються без вмісту зон).
  Зона, прив'язана до текстового поля запису, — лише прості абзаци. Значення перевіряє `paperwork/paper-fields.ts` за спільними правилами
  (`normalizeValue`), межі — тісніші з поля шаблону й поля запису; варіанти `enum` — з довідника чи схеми, архівний лишається, де вже обраний.
  Поля `fill: staff` (і їхні зони) змінюють лише admin і moderator (`papers.fill_staff`). Обов'язковість перевіряє публікація.
  Відповідь з документом несе версію шаблону з готовими полями (межі, варіанти, `canFill`): окремого права на читання версії не треба.
  Обраний у документі пункт довідника не видаляється (`DictionaryUsageRegistry`). Текст значення («01.12.2026», «так», назва варіанта)
  рахує спільний `valueText` — однаково на аркуші й у друці.
- **Посилання документа на записи** — значення полів `ref:*` (id запису у `values`) і «@» у тексті (вузол `mention` з `type` і `id`, без назви:
  назва завжди береться з самого запису, як його бачить читач; невидимий чи видалений — «запис недоступний»). Збереження документа
  (`paperwork/paper-refs.ts`) перевіряє лише нові для документа записи — існують і видимі людині (`find` з `LinkRegistry`), а вже наявні
  приймає й після видалення запису, щоб документ далі зберігався. У тій самій транзакції сервер приводить зв'язки документа
  (`from_type = 'paper'`) до вмісту: поле — роль із ключем поля, «@» — без ролі; додає лише записи, про які відомо, що вони є
  (щойно перевірені або вже пов'язані), пара, пов'язана навпаки, лишається як є (`ON CONFLICT DO NOTHING`). Ці зв'язки — частина
  збереження документа, тож окремо в аудит не пишуться. Так документ з'являється в «Пов'язане» запису й знайдеться для «нове про мене».
  `ref:<тип>` у шаблоні публікується лише для типів із `LinkRegistry` — інших пікер не знайде.
- **Публікація документа** (`POST /papers/:id/publish`, `papers.publish`) — одна транзакція: обов'язкові поля заповнені; документ шаблону
  `creates` створює запис через **адаптер** модуля; шаблон із префіксом дає номер з `paper_counters` (`prefix`, `year`, `last`;
  `INSERT … ON CONFLICT DO UPDATE … RETURNING` — однакових номерів не буває навіть при одночасній публікації). Номер живе лише в `papers.number`.
  **Читач** (`RecordReader` у `paperwork/adapters.ts`: `resolve` — запис зараз за ключами його схеми) модуль реєструє
  `registerReader` у `PaperAdapterRegistry`: про такі записи бувають звіти (`report`). Читачі є в обладнання (`places/place.reader.ts`),
  несправностей (`faults/fault.reader.ts`) і проєктів (`projects/project.reader.ts`: учасники — `memberIds`); адаптер — теж читач,
  тож звіт буває й про ТЗ, стягнення, нарахування, допуск, списання.
  Адаптер (`PaperAdapter` у `paperwork/adapters.ts`) модуль реєструє в `PaperAdapterRegistry` у `onModuleInit` (`register`), як зв'язки:
  `publish` (створити запис зі значень прив'язаних полів через сервіс модуля — з `assertCan`, аудитом і кодами помилок; DTO перевіряється
  як у контролері, `recordInput`), `cancel` (зняти запис; отримує й id документа, який скасовується), `resolve` (запис зараз — для прив'язаних полів і `ready` для фіксації),
  `canView` (хто бачить документи через їхні записи: усі, ніхто або умова SQL над документом `p` — за `p.target_id` чи `p.id`), `canUpdate` і `update` (змінити запис з
  опублікованого документа — див. нижче), `adopt` (запис, створений до документів, отримує документ: модуль перевіряє право й стан
  і, якщо треба, запам'ятовує документ). Методи сервісу модуля, які кличе адаптер,
  приймають `EntityManager` транзакції публікації. Помилку запису з `field` (ключ поля запису) сервер повертає з ключем поля шаблону.
  Редактор не знає розділів: тип `creates` дозволено лише для типів з адаптером, `report` — з читачем (`GET /papers/templates/targets`). Адаптери є в ТЗ,
  дисципліни, балів, допусків і складу (`publish` отримує й id документа, який публікується).
  Склад (`inventory/inventory-writeoff.adapter.ts`, тип `inventory_writeoff`): рядок «Акта списання» — `InventoryService.writeOff`
  у транзакції документа (рух з мінусом, як «Взяти», `inventory_movements.paper_id` — акт; нестача — `INSUFFICIENT_STOCK`, дробове для
  «шт» — `INTEGER_REQUIRED`, обидва з рядком); списання після публікації не змінюється, старим рухам акт не додається (`adopt` — 403);

  `paper_id`, журнал рухів не змінюється; акти бачать усі. ТЗ (`tasks/task.adapter.ts`): створити — `tasks.create` (admin, moderator), змінити — `tasks.update` (`tasks.manage`, доки ТЗ не виконане),

  видаляється з причиною в аудиті, файли — після коміту), ТЗ бачать усі. Опублікований документ отримує `target_type`, `target_id`

  документа; без документа ТЗ лише знімається з причиною (`POST /tasks/:id/cancel`). Запис, створений до документів, отримує документ
  через `POST /papers/for-record` (`PaperworkService.forRecord`): шаблон `creates` його типу, право й стан — `adopt` адаптера (ТЗ — `canUpdate`;

  прив'язаних полів — з `resolve` (шаблон «рядок = запис» — один рядок), одразу «Опубліковано» з номером і `@target`; один запис — один документ (`PAPER_TARGET_TAKEN`,

  `withZoneText` для зон); без запису — записані значення. Скасування (`papers.cancel`) — з причиною, документ лишається.
  **Звіт** (`report`) запису не створює й `target_*` не має: `target_type`/`target_id` означають «запис, який документ створив» (на них
  тримаються скасування запису, `PAPER_TARGET_TAKEN`, права фіксації, номер на картці ТЗ). Свій запис звіт бере з поля запису —
  першого неприв'язаного поля `ref:<тип шаблону>` (`reportRecordKey` у `template-fields.ts`; публікація версії вимагає його обов'язковим,
  незмінним, поза умовними блоками — `reportProblem`, `TEMPLATE_REPORT_RECORD`), тож зв'язок із записом — звичайний зв'язок поля, і звіт
  з'являється в «Пов'язане». Прив'язані поля звіту — авто (`isAutoBinding`); `shown` бере запис читачем (`recordOfReport`) уже в чернетці
  (лише `values`: чернетка зберігає свій вміст, тож зона із записом була б зміною заблокованої зони; фронт не надсилає авто-поля й після
  збереження поля запису читає документ знову), після публікації — і зони. Права звіту — як у вільного документа (`ownerId`).

  з `{ report: type }`), документ — через `about`; кнопки немає, коли таких шаблонів людина не має.

  поля шаблону. Джерело (`TableSource` у `paperwork/tables.ts`: назва, тип поля `input`, стовпці, `rows(value, reader, m)`) модуль реєструє
  в `PaperTableRegistry` у `onModuleInit`: допуски, журнал сеансів (`places/place.tables.ts`), несправності (`faults/fault.tables.ts`) —
  для `ref:place`, рейтинг за місяць (`points/points.tables.ts`, `PointsService.ranking`) — для `date`, «Технічні завдання проєкту» (`tasks/task.tables.ts`:
  ТЗ, пов'язані з проєктом зв'язком у будь-який бік, з номером документа) і «Матеріали проєкту» (`inventory/inventory.tables.ts`: рухи
  складу з цим проєктом) — для `ref:project`. Клітинки — готовий текст, рядки — від
  найдавнішого, не більше `TABLE_MAX_ROWS` (200) останніх, решта — «… і ще N». Хто що бачить, вирішує джерело тим самим правилом, що й
  розділ (сеанси й допуски учасника — лише свої). `PaperworkService.tablesOf`: до фіксації таблиці живі для читача (`PaperDto.tables`,
  друк без знімка); `snapshot` бере їх як модератор і пише в `papers.tables` (міграція `PaperTables`; `NULL` — не фіксували), далі документ
  показує записане; повторна фіксація звіту — свіжі. Перевірка версії (`tableProblem` у `template-fields.ts`): джерело є, поле його типу,
  `required` або прив'язане, не в умовному блоці й не стовпець; джерело зникло — «потребує оновлення». Рендер — `autoTableInner`
  (`render.ts`), той самий у редакторі (`AutoTable` у `editor/structure.ts`, дані — `SheetInfo.table`). У конструкторі — блоки групи «Авто»
  з джерел (`GET /papers/templates/targets`, `tableBlocks`): блок бере перше поле свого типу на аркуші (обов'язкове чи прив'язане; запис
  звіту) або створює нове обов'язкове (`tableField`); поле таблиці — поле версії, навіть якщо більше ніде не стоїть. Документ після
  збереження поля таблиці читає себе знову (відповідь `PATCH` — без вмісту).
  У ТЗ є `submitted_at` (остання здача) і `accepted_by_id` (хто прийняв; час прийняття — `completed_at`): міграція `TaskReview`
  заповнила їх для наявних ТЗ з аудиту.
  **Фіксація** (`POST /papers/:id/freeze`, `papers.freeze`; `PaperworkService.snapshot`) — коли записи документа готові (`resolve().ready`
  адаптера; записи рядків — усі; вільний — завжди). Аркуш рендерить сервер (`sheetHtml` у `print.ts`: `<main class="paper">` з
  `data-paper` і `data-snapshot`, тож однаковий текст двох документів не дає однакового хешу), записи названо повністю (як їх бачить
  модератор) — знімок однаковий для всіх читачів. `paper_snapshots` (`paper_id`, `n`, `html`, `sha256` — унікальний, `resolved_values`,
  хто й коли) лише доповнюється; хешується саме збережений HTML, печатка (QR, SHA-256) і водяний знак — поза ним, на сторінці друку,
  бо QR несе хеш. Документ отримує показані значення й вміст (прив'язані поля більше не йдуть за записом: `shown` живий лише
  в «Опубліковано»), стан `frozen` і зв'язки за показаним (виконавці ТЗ знаходять документ у «нове про мене»).
  **Автофіксація** (`autoFreeze` шаблону) — у тій самій транзакції: після публікації й `for-record`, якщо записи вже готові (стягнення,
  нарахування), і коли модуль каже, що запис готовий, — `PaperworkService.recordReady(type, id, actor, m)` (ТЗ: `accept` у транзакції
  приймання). Редактор не знає, що таке «прийняти ТЗ»: модуль сам кличе `recordReady`. Документ фіксується один раз (`PAPER_FROZEN`),
  крім звіту (`freezable`): зафіксований чи підписаний звіт фіксується знову — `shown(…, fresh)` читає запис наново, знімок `n` + 1,
  стан знову `frozen`; скан — до знімка, тож новий знімок чекає свого. `PaperDto.snapshots` — усі знімки (фронт: «Версії: 1 · 2»). `GET /papers?due=freeze` — що чекає кнопки: опубліковані без автофіксації,
  готовність перевіряють адаптери, тому сторінки — після перевірки (таких документів небагато).
  **Підпис** (`POST /papers/:id/signed`, `papers.sign` — те саме правило, що й фіксація; `PaperworkService.sign`) — скан чи фото паперу
  до зафіксованого документа (підписаного — ще раз: кращий скан). Файл перевіряє й зберігає модуль Архіву (`DocumentsService.store`,
  `insertDoc`, `insertVersion` у транзакції документа; ними ж працюють `POST /documents` і `/documents/:id/files`): скан — версія
  архівного документа знімка (`paper_snapshots.archive_doc_id`, унікальний; перший скан створює документ, наступні — версії).
  Категорія — пункт `signed_papers` «Підписані документи» довідника `document_category`: `ensureDictionaryItem` бере пункт із цим ключем
  або з цією назвою, інакше створює його (і коли його видалили до першого скану). Архівний документ — `supervisors`: скан, скажімо,
  подання про стягнення не має потрапити до всіх; хто бачить документ редактора, відкриває скан через нього (`GET /papers/:id/signed`).
  Документ стає `signed`; скасування скан не прибирає.
  **Графічний підпис** (`POST /papers/:id/signatures`, `papers.sign_drawn`; `PaperworkService.signDrawn`). Рішення:
  (1) хто підписує — фіксується разом зі знімком: `paper_snapshots.signers` — рядки підпису аркуша в його порядку (`signLines` у
  `shared/editor-schema/render.ts` — той самий обхід, що й `structureInner`: «Затверджую», колонки «Блоку підписів», права — лише з назвою)
  з `userId` того, кого аркуш назвав (`signersOf`: автор, підписант з реквізитів, учасник поля `ref:user` зі значень знімка); рядок без імені —
  `null`, лише скан. Знімки, зроблені до графічного підпису, мають `signers = null` — лише скан, нічого не вгадуємо. (2) Підписує лише та людина, яку чекає рядок, —
  контекст `signer` у `policy.ts`, без винятку для адміна (`NOT_SIGNER`): підпис — не право, а твердження «це я». Один запит підписує всі
  ще не підписані рядки людини в останньому знімку. (3) Підпис — штрихи (`strokes`, цілі точки на полі 1500 × 500 з лімітами,
  `shared/editor-schema/signature.ts`), не файл: зберігати зображення не треба, а SVG (один `<path>` з атрибутами, без `style`) будує
  `signatureSvg` — сервер для друку, редактор для свого аркуша, однаково; CSP не слабшає. Малюють щоразу (у профілі підпис не зберігається). `paper_signatures` (знімок, рядок — унікальні разом, хто, штрихи, коли)
  лише доповнюється; помилку виправляє скасування документа. Знімок і SHA-256 не змінюються: друк і DOCX накладають підписи на аркуш
  знімка (`signedSheet`: малюнок у лінії, під нею «Підписано в DigiComp HUB …»; у DOCX — лише цей рядок з ім'ям). Усі рядки з людьми
  підписано — документ `signed` (зі сканом він уже `signed`, графічно підписати все одно можна). Нова фіксація звіту — нові рядки;
  підписи старого знімка лишаються при ньому. «На мій підпис» (`due=sign`) — SQL над `signers` останнього знімка без підпису людини.
  Перевірка (`/papers/verify/:sha`) показує, хто й коли підписав. (4) **Підпис разом із фіксацією:**
  хто фіксує документ і стоїть на рядку нового знімка, підписує його тим самим запитом — інакше дія не виконується. Перевірка — в одному
  місці, `snapshot()`: після `signersOf`, до запису знімка; рядки людини без `strokes` — `PAPER_SIGNATURE_REQUIRED` з `paperId`,
  `number`, `title`, `lines`, і транзакція відкочується разом зі зміною модуля (прийняте ТЗ, бали, стягнення, номер). Зі `strokes` —
  `addSignatures` (спільний із `signDrawn`) у тій самій транзакції. Тому `strokes?` (`FreezeSignatureDto`) приймають усі дії, що можуть
  зафіксувати документ: `POST /papers/:id/freeze`, `/publish`, `/for-record` і `POST /tasks/:id/accept` (через `recordReady`).
  Фронт не вгадує, чи потрібен підпис: шле дію без нього, на цю помилку `useSignWith` (`web/src/editor/`) відкриває `SignaturePad`
  з рядками з відповіді й повторює ту саму дію з малюнком; «Скасувати» — нічого не змінено.
  Фронт: «Підписати» (`canSignDrawn`) відкриває `SignaturePad` (`web/src/editor/`): `pointer events` з `touch-action: none` і захопленням
  вказівника, один вказівник за раз; точки — одразу цілі на полі 1500 × 500, ближчі за 4 одиниці відкидаються, по досягненні лімітів
  `SIGN_LIMITS` нові не пишуться (сервер завжди прийме намальоване); малюнок — той самий `strokesPath`, що й на аркуші. Вікно —
  `role="dialog"` з власним фокусом і Esc (у jsdom немає `showModal`), вужче 900 px — на весь екран. Аркуш редактора показує підписи
  через `SheetInfo.signatures`: декорація структурного блоку несе номер його першої лінії (`nodeSignLines`, той самий порядок, що
  `signLines`), а `signedSheet(html, signatures, first)` вставляє малюнок і примітку (`signedNote`) так само, як у друці. Сторінка
  виконаного ТЗ читає його документ і, якщо `canSignDrawn`, пропонує «Підписати документ» (необов'язково) — тим, кого рядок чекає й досі
  (автору, підписанту «Затверджую»; хто прийняв, уже підписав).
  **Зображення** (`PaperImagesService`, `/paper-images`). Документ зберігає лише id (`image` у
  `shared/editor-schema/`: `width` 25/50/75/100 %, `align`, `alt` — класи `paper-image img-w-* img-left|right`, без `style`); файл —
  `paper-images/<id>.png|jpg` у `files_data`, ніколи не перезаписується, тож знімок з посиланням на id лишається тим самим. Не файл Архіву й
  не в кошику. Приймаються PNG і JPEG за заголовком (`image-info.ts`, без декодування й залежностей), до 5 МБ і 2000 px з боку: браузер
  сам зменшує й перекодовує. Хто бачить зображення, йде за документами: `paper_image_uses` — зображення ↔ документ або версія шаблону
  (зовнішні ключі з каскадом, рівно один); правило `paper_images.read` — завантажив сам або `shared`: його тримає документ, який людина бачить
  (`whereSeen`), чи версія шаблону, яку бачить. Збереження чернетки чи версії шаблону, створення, копія й зміна опублікованого перевіряють
  лише нові зображення (`checkNew`, з `FOR KEY SHARE` до коміту) і оновлюють використання там само, де `syncLinks`: чернетка — її вмістом,
  документ після публікації — лише додає (знімки посилаються на старі). Невживані старші за добу сервер видаляє щогодини (`purgeUnused`);
  зображення, яке хтось саме ставить у документ, тримає замок і зовнішній ключ — видалення відкладається до наступного разу. DOCX бере
  файли зображень аркуша (`files`) і вкладає їх (`ImageRun`); CSP друку — `img-src 'self'`.
  Фронт: вузол `Image` (`editor/image.ts`; `insertImage` ставить після виділеного блоку чи в точку й виділяє вставлене; вставку з буфера
  й перетягнуті файли віддає `storage.image.onFiles`) і `useImages` (`editor/images.ts`): файл → `createImageBitmap` (поворот за EXIF) →
  canvas до 2000 px → PNG лишається PNG (понад 5 МБ — JPEG), решта — JPEG на білому з якістю 0,9…0,5 → `POST /paper-images`. Метадані
  камери зникають разом зі старим файлом. Перед завантаженням `can().insertImage` — туди, де аркуш зображення не прийме (текст шаблону,
  проста зона), нічого не вантажиться. Стрічка: «Вставка → Зображення», у виділеного — група ширини, боку, опису й «Видалити» (в обох
  вкладках); на телефоні — кнопка в рядку форматування. Конструктор: блок `image` (`kind: 'image'`) спершу просить файл, ставиться
  `placeBlock` з id і виділяється.
- **Архів як єдиний пошук** — модуль `archive` (`ArchiveService`, `GET /archive`; право `documents.read`). Він залежить від `paperwork`
  (а той — від `documents`), тому список не живе в жодному з них. Два джерела, кожне зі своєю видимістю: файли — як `/documents`
  (`supervisors` — лише staff, `archived=true` — лише staff і лише файли), документи редактора — `whereSeen` (правило `papers.read`)
  і лише ті, що мають знімок (`EXISTS paper_snapshots`: зафіксовані, підписані, скасовані після фіксації; документ виконаного ТЗ потрапляє
  сюди автофіксацією). Архівний документ сканів (`paper_snapshots.archive_doc_id`) у список не йде: підписаний скан — це стан документа,
  а не окремий рядок. Фільтр, що стосується лише одного джерела (`status` — документів, `category` — файлів), вимикає друге.
  Рік — за київським часом: документа — `published_at` (той самий рік, що в номері), файлу — `created_at`. Сторінки: кожне джерело
  віддає перші `page × limit` рядків за `updated_at`, сервіс зливає їх і вирізає сторінку; `total` — сума. Записів в Архіві небагато,
  тож це простіше за спільний SQL над двома таблицями. Роки й категорії для чипів рахуються з видимого без фільтрів.
  `GET /papers?due=sign` («На мій підпис») — зафіксовані за 30 днів без скану, де читача чекає ще не підписаний рядок останнього знімка
  (`paper_snapshots.signers`, див. «Графічний підпис»);
  `due=scan` — зафіксовані за 30 днів без скану, які читач може підписати. Межа в 30 днів: підпис необов'язковий, тож без неї списки
  Головної лише росли б.
  **Перевірка** — `GET /papers/verify/:sha` (`papers.read`, тобто кожен, хто ввійшов) і сторінка застосунку `/papers/verify/:sha`,
  куди веде QR (`PUBLIC_ORIGIN`). Справжність, стан і причину скасування бачить кожен; `paperId` (відкрити, друк знімка) — лише хто бачить документ:
  хто перевіряє, той уже тримає папір.
  **Дисципліна лише через документ** (`discipline/discipline-record.adapter.ts`): у модуля немає видачі з API — `DisciplineService.issue`
  кличе тільки адаптер у транзакції публікації (право `discipline.issue` з учасником: модератор — не собі; штраф знімає бали).
  Стягнення не змінюється (`canUpdate` — ні); скасування документа знімає його `revokeByPaper` (admin — будь-яке, moderator — видане собою;
  штраф повертає бали; аудит `discipline.revoked` з `byPaper`). Стягнення з документом через `POST /discipline/:id/revoke` не знімається
  (`DISCIPLINE_HAS_PAPER`); видане до документів — як раніше, і воно ж отримує подання через `for-record` (`DisciplineService.adopt`:
  право `discipline.revoke` — admin будь-яке, moderator видане собою; зняте — `ALREADY_REVOKED`). Документ стягнення учасник бачить лише про себе (`canView` — умова SQL
  за `discipline_records.user_id`). `DisciplineRecordDto` несе `paper` (подання) і `papers` — документи, що посилаються на стягнення
  й видимі читачеві (`papersReferring` у `paper-targets.ts`: зв'язки від документів, крім `@target`), — так видно «Пояснювальну записку».
  **«Рядок = запис».** У шаблоні `creates` можна прив'язати стовпці одного блоку «Повторювані рядки» (`bindingProblem` з картою стовпців
  `rowColumns`; лише до полів, які задаються при створенні): тоді кожен непорожній рядок — окремий запис, поза блоком нічого не
  прив'язується, блок обов'язковий і без «можна змінити». Публікація кличе `publish` адаптера на кожен рядок по черзі в тій самій
  транзакції (`recordRows` у `paper-fields.ts`); помилка — з `field` блоку й `row`, і тоді нічого не створюється. Документ отримує
  `target_type` без `target_id`, а свої записи знає зі зв'язків `@target` (`recordsOfPaper` у `paper-targets.ts`) — їх знімає скасування.
  Рядки показують записані значення (записи таких типів не змінюються); `for-record` для такого шаблону робить документ з одним рядком
  із запису (`target_id` — `NULL`, запис — у зв'язку `@target`).
  **Бали лише через документ** (`points/points-entry.adapter.ts`): ручного нарахування з API немає — `PointsService.award` кличе тільки
  адаптер у транзакції публікації «Відомості балів» (право `points.award` з учасником: модератор — не собі); нарахування пише
  `points_ledger.paper_id` (зовнішній ключ на `papers`; міграція `PointsLedgerPaper`). Нарахування не змінюються; скасування відомості
  знімає кожне `revokeByPaper` (admin — будь-яке, moderator — своє; аудит `points.revoked` з `byPaper`). Нарахування з відомістю через
  `POST /points/:id/revoke` не знімається (`POINTS_HAS_PAPER`); зроблене до документів — як раніше, і воно ж отримує відомість з одним
  рядком через `for-record` (`PointsService.adopt`: лише ручне й не зняте, право `points.revoke` — admin будь-яке, moderator своє;
  пише `paper_id`). Відомість учасник бачить, якщо він є
  в її рядках (`canView` — умова SQL за `points_ledger.paper_id`). Історія балів несе `paper` — відомість запису.
  **Допуск лише через документ** (`places/place-authorization.adapter.ts`): `POST /place-authorizations` немає — `PlacesService.grant`
  кличе тільки адаптер у транзакції публікації «Запису про інструктаж і допуск» (`places.authorize`; учасник активний, обладнання не
  в архіві — інакше `PAPER_FIELD_INVALID` з полем). Пара учасник + обладнання має один допуск (`UNIQUE`), тож повторний інструктаж
  оновлює той самий рядок (термін, примітку, хто й коли видав) і пише `place_authorizations.paper_id` — документ чинного терміну
  (міграція `AuthorizationPaper`; кілька документів мають той самий `target_id`, допуск знає свій). Скасування документа знімає допуск,
  лише якщо `paper_id` — цей документ (`revokeByPaper`, аудит `authorization.revoked` з `reason` і `byPaper`); документ раніших
  інструктажів лишається історією. Допуск з документом через `DELETE /place-authorizations/:id` не відкликається
  (`AUTHORIZATION_HAS_PAPER`); виданий до документів — як раніше, і він же отримує документ через `for-record` (`adopt`: staff, пише
  `paper_id`). Учасник бачить документи допуску, що посилаються на нього полем (`canView` — умова SQL за `record_links` до `user`, роль —
  ключ поля): так і після того, як допуск зняли. `AuthorizationDto.paper` — документ чинного терміну.
  **Документи на Головній і в Профілі:** блок «Документи» на Головній — «Мої чернетки» (`GET /papers?mine=true&status=draft`)
  і «Нове про мене» (`?about=me`: не чернетки інших авторів зі зв'язком документа на читача; змінені за 14 днів — відбирає клієнт), по 5;
  у Профілі в картці «Моє» — «Мої документи» (`?mine=true`, 10 останніх і кількість, решта — «Редактор» → «Мої»).
  Старі стягнення й ручні нарахування мають на своїх сторінках «Створити документ» (поруч із «Зняти», за тією самою умовою).
  **Авто-поля:** поле шаблону `creates`, прив'язане до поля запису без `create` (ТЗ: виконавці, розподіл балів, здано, виконано, прийняв), —
  авто-поле (`isAutoBinding`, `auto` у полі документа): не обов'язкове, без «можна змінити», його ніхто не заповнює й публікація не передає
  в запис; до публікації — сіре «заповниться після публікації», після — `resolve` запису. «Розподіл балів» — обчислюване поле схеми ТЗ
  `pointsSplit` (`splitPoints` у порядку, в якому виконавці взяли ТЗ). Назви записів документа (`refs`) рахуються від того, що він показує.
  **Зміна опублікованого документа** (`PATCH /papers/:id` у стані «Опубліковано», `PaperworkService.change`): змінюються лише поля
  з `editable`, не авто, свої за `fill`; прив'язане — коли адаптер дозволяє (`canUpdate`), і тоді запис змінює `update` адаптера в тій самій
  транзакції (права, перевірки й аудит модуля; помилка з `field` — з ключем поля шаблону, і для 409); неприв'язане — автор документа,
  admin і moderator (`papers.change`). Змінене визначається порівнянням із тим, що документ показує. У редакторі це окремий режим
  «Змінити» → «Зберегти зміни» без автозбереження: одне збереження — одна зміна запису й один запис аудиту `paper.updated`.
  «Авто: номер» — вузол `paperNumber` спільного опису: на аркуші — номер або «з'явиться після публікації», у друці — номер або лінія
  (так само «Авто: дата» — `paperDate`).
- **Умовний блок** — вузол `conditional` спільного опису (лише на верхньому рівні, не один в одному) з умовою: поле шаблону (`field`)
  і що воно має (`value`, `conditionHolds` у `fields.ts`): вибір — ключ варіанта (`enum` — обрано, `list<enum>` — серед обраних),
  прапорець — `@yes` / `@no` (позначено / ні), будь-яке інше поле, яке заповнюють, — `@filled` (заповнено). Зона й «Повторювані рядки»
  умовою не бувають (`conditionKind`). Поки умова не виконується, блок «вимкнений» (`offFields`): його поля не обов'язкові,
  не друкуються (`FieldFill.holds`), не йдуть у запис; чернетка значення тримає (обрали знову — повернулися), публікація й зміна
  опублікованого їх прибирає, зони блоку — спорожнює. Публікація версії перевіряє: поле умови може бути умовою, людське (не авто), стоїть поза
  умовними блоками й не стовпець, `value` пасує до його виду (`conditionFits`; варіант — серед його варіантів); поле блоку — лише в цьому
  блоці й не прив'язане до обов'язкового поля запису
  (`bodyProblem`, `conditionProblem` у `template-fields.ts`). У вільному документі умовного блоку немає (`PAPER_CONTENT_LOCKED`).
  На аркуші вимкнений блок прихований, Tab його оминає; панель «Поля» й «Форма» не показують його поля й не рахують їх
  (`editor/conditional.ts`), а під увімкненим полем пишуть, чому воно з'явилося. Конструктор показує блок жовтою рамкою з умовою
  словами. Блок «Умовний блок» (група «Структура», `blocks/conditional.ts`) вставляється з умовою на перше поле, яке може нею бути
  (`conditionFields` у `editor/template.ts`); такого поля немає — блок у палітрі неактивний із поясненням. «Властивості» міняють поле
  й значення; «Прибрати умову» лишає вміст на аркуші (`unwrapBlock`). Перейменування поля умови міняє й умову, видалення — знімає рамку.
- **Повторювані рядки** — вузол `repeat` спільного опису (лише на верхньому рівні, не в умовному блоці) з ключем поля шаблону типу
  `rows` (тип лише шаблону, у записах його немає) і рівно однією таблицею: рядки над останнім — шапка, останній повторюється.
  Його поля — **стовпці** (`rowsOf`); «№ рядка» — вузол `rowNumber`, лише в блоці (`checkContent`). Значення поля — список рядків,
  рядок — значення стовпців за їхніми ключами (`{ "rows1": [{ "member": "…", "points": 5 }, {}] }`; порожня клітинка — без ключа).
  Документ тримає таблицю як у тілі шаблону, рядки — у `values`. Стовпці — звичайні поля версії, але документ отримує їх у `columns`
  поля рядків (`resolveFields`): хто заповнює, «можна змінити» й друк — як у блоку; «Обов'язкове» блоку — хоча б один непорожній рядок,
  стовпця — клітинка в кожному непорожньому рядку; найбільше рядків — `maxItems` блоку (без нього 50, до 100). Чернетка тримає щойно
  додані порожні рядки; публікація й зміна опублікованого їх прибирають. Помилка в рядку — `field` (ключ блоку) і `row` (номер від 0).
  Посилання з клітинок пишуться у зв'язки документа з роллю — ключем стовпця. Публікація версії перевіряє (`repeatProblem`): поле
  рядків — лише блоком і раз; у шапці немає полів і «№ рядка», у блоці — зон; стовпець — не зона, не рядки, ніде більше на аркуші
  (не підписант, не умова, не в іншому блоці); прив'язка стовпців — «рядок = запис» вище. У вільному документі блоку немає
  (`PAPER_CONTENT_LOCKED`). Друк: шапка, далі рядок на кожне значення; рядків немає — один порожній, щоб заповнити від руки.
  На аркуші документа блок малює `repeatView` (`editor/repeat.ts`) зі значень: текст блоку не змінюється, клік по клітинці відкриває
  її в панелі, Tab переходить на блок цілком. Рядки додаються й прибираються лише в панелі «Поля» й «Формі» (`fieldTypes/rows.tsx`).
  У конструкторі блок — звичайна таблиця з жовтою міткою й позначеним нижнім рядком; поле в шапку, зону в блок і стовпець поза
  блоком він не пускає (`badFields`). У «Властивостях» стовпця шаблону `creates` є «Зв'язок із записом» (`bindingOptions` з картою стовпців);
  щойно стовпець прив'язано, блок стає обов'язковим і незмінним, а замість його перемикачів — пояснення «Рядок = запис».
- **Новий документ «про запис»** — `POST /papers { templateId, about: { type, id } }`: запис стає значенням першого поля шаблону
  `ref:<type>`, яке людина заповнює (не авто), а без такого — першого такого стовпця «Повторюваних рядків» (перший рядок),
  і перевіряється, як будь-яке збереження (існує, видимий). Шаблон без такого поля — документ без значень. Список шаблонів несе `about` — типи, на які посилаються поля поточної версії, тож розділ знаходить шаблони
  для свого запису, не знаючи їх назв (профіль: «Пояснення» до стягнення; «Нове подання» і «Нова відомість» для учасника).
- **Шаблони документів** — `paper_templates` (назва, вид `creates`/`report`/`free`, тип запису, префікс номера, автофіксація,
  хто створює документи, видимість нових, поточна версія, архів) і `paper_template_versions` (номер, `body jsonb`, `fields jsonb`,
  версія схеми запису, `revision`, хто й коли опублікував). Вид і тип запису не змінюються: на них стоять прив'язки опублікованих версій.
  Опублікована версія незмінна; чернетка в шаблону одна (частковий унікальний індекс). Під час збереження чернетки перевіряється лише форма
  полів — конструктор зберігає й недоналаштоване; під час публікації — усе (`paperwork/template-fields.ts`): межі за типом, довідник,
  прив'язки до схеми запису (той самий тип, не ширші межі, у `creates` — усі обов'язкові поля запису) і звірка тіла з полями
  (кожне поле в тілі, зона — одна й лише для `richtext`, без невідомих ключів і полів у зонах).
  Документ створюється лише з поточної версії шаблону, що не в архіві й не потребує оновлення (`TemplatesService.forPaper`). «Потребує оновлення» не зберігається:
  під час читання, якщо версія схеми (`publishSchema().version`) інша, ніж при публікації, прив'язки перевіряються знову.
  Довідники полів опублікованих версій зареєстровані в `DictionaryUsageRegistry`. Контролер шаблонів зареєстровано перед контролером
  документів, щоб `/papers/templates` не потрапляв у `/papers/:id`.
  Початкові шаблони «Протокол зборів» (`ПЗ`, створюють усі) і «Інструкція з безпеки» (`ІБ`, лише модератори й адмін; поле `ref:place`)
  додає міграція `StarterTemplates` — вільні, видимі всім, опубліковані v1 від імені першого активного адміна. На новій установці міграції
  проходять раніше, ніж з'являється адмін, тож нічого не додають; тоді `POST /auth/setup` запускає всі міграції початкових шаблонів знову
  (`paperwork/seed-templates.ts`, список звіряє `seed-templates.spec.ts`, e2e — `test/setup.e2e-spec.ts`): вони додають лише відсутні шаблони за сталими `id`.
  тест `paperwork/starter-templates.spec.ts` перевіряє їх правилами публікації. Відкат прибирає лише ті, з яких ще немає документів.
  Шаблони «Технічне завдання» (за макетом: шапка, «Затверджую», мета, вимоги, параметри, критерії, підписи «Завдання видав» / «Роботу прийняв»)
  і «Коротке ТЗ» додає міграція `TaskTemplates` так само: `creates` → `task`, префікс `ТЗ`, лише модератори й адмін, видимі всім, автофіксація;
  поля, крім авто, — «можна змінити»; обов'язкові — лише назва й бали (термін, вимоги й критерії — ні, щоб старі ТЗ без них змінювалися);
  `schema_version` — `NULL` (прив'язки перевіряються за схемою зараз). Тест — `paperwork/task-templates.spec.ts` (зі справжньою схемою ТЗ).
  Міграція `DisciplineTemplates` так само додає «Подання про стягнення» (`creates` → `discipline_record`, `ПС`, лише модератори й адмін,
  видиме автору, автофіксація; «Кому», «Вид стягнення», «Розмір штрафу, балів» в умовному блоці «Штраф», зона «Підстава»; жодне поле
  не змінюється після публікації) і «Пояснювальну записку» (вільна, без номера, створюють усі, видима автору; «Стягнення» —
  `ref:discipline_record`, зона «Пояснення»). Тест — `paperwork/discipline-templates.spec.ts`.
  Міграція `PointsTemplates` так само додає «Відомість балів» (`creates` → `points_entry`, `ВБ`, лише модератори й адмін, видима автору,
  автофіксація; шапка, номер, дата, таблиця «№ | Учасник | Бали | За що» — стовпці прив'язані, рядок = нарахування; підпис «Склав»;
  книжкова сторінка). Тест — `paperwork/points-templates.spec.ts`.
  Міграція `ReportTemplates` так само додає «Паспорт обладнання» (`report` → `place`, `ПО`, лише модератори й адмін, видимий автору:
  поля обладнання — авто, таблиці «Допуски», «Несправності», «Журнал сеансів»), «Акт несправності» (`report` → `fault`, `АН`, лише модератори
  й адмін, видимий усім: поля несправності, зона «Висновок», підписи «Склав» / «Погоджено») і «Рейтинг за місяць» (вільний, `РМ`, лише
  модератори й адмін, видимий усім: поле «Місяць (будь-який його день)» лише для таблиці, над таблицею — місяць). Без автофіксації. Тест —
  `paperwork/report-templates.spec.ts` (зі справжніми схемами й джерелами).
  Міграція `AuthorizationTemplates` так само додає «Запис про інструктаж і допуск» (`creates` → `place_authorization`, `ІД`, лише модератори
  й адмін, видимий автору, автофіксація; «Учасник», «Обладнання», «Допуск діє до», «Примітка» — прив'язані, зона «Зміст інструктажу»;
  підписи «Інструктаж провів» (автор) / «Інструктаж отримав» (учасник); жодне поле не змінюється після публікації). Тест —
  `paperwork/authorization-templates.spec.ts`.
  Міграція `ProjectInventoryTemplates` так само додає «Паспорт проєкту» (`report` → `project`, `ПП`: поля проєкту — авто, зона «Мета й
  очікувані результати», таблиця «ТЗ проєкту»), «Підсумковий звіт» (`report` → `project`, `ЗП`: досягнення, «ТЗ проєкту», «Матеріали
  проєкту», джерела, зона «Висновки»; обидва з підписами «Склав» / «Погоджено», без автофіксації) і «Акт списання» (`creates` →
  `inventory_writeoff`, `АС`, автофіксація: «Затверджую», таблиця «№ | Позиція | Кількість | Причина» — рядок = списання, зона «Примітка»,
  підпис «Склав»). Усі — лише модератори й адмін, видимі всім. Тест — `paperwork/project-inventory-templates.spec.ts` (і що префікси не
  збігаються з іншими шаблонами: лічильник номерів — один на префікс).
  Окремого шаблону «Порожній документ» немає: це пункт «Новий документ» без шаблону.
- **Бали** — книга обліку (`points_ledger`): записи не змінюються, зняття додає компенсаційний запис. Баланс — сума.
  Ручне нарахування посилається на свою «Відомість балів» (`paper_id`).
- **Бункер** — `bunker_cards` (вид, назва — лише катастрофа й загроза, текст, дія особливої умови, автор, `builtin`), `bunker_packs`
  і `bunker_pack_cards` (карта буває в кількох паках), `bunker_rooms` (налаштування й стан гри в `jsonb`, `last_action_at`),
  `bunker_room_members` (хто в кімнаті, коли востаннє питав новини; унікальний `user_id` — одна кімната на людину).
  Базовий пак (`builtin`) додає міграція `Bunker`; його не змінює ніхто, роблять копію. Тест — `bunker/base-pack.spec.ts`.
  Стан гри секретний: роздані карти — копії (зміна паку гри не чіпає), колода, бюлетені. Назовні він іде лише через `viewFor`.
- **Час** — у базі UTC, усі часові колонки — `timestamptz`; дні, місяці рейтингу, дедлайни й журнал рахуються за київським часом.
- **Бекап** — щодня о 03:30 база й файли (і конфігурація HA), зберігаються 14 останніх. Див. [OPERATIONS.md](OPERATIONS.md).

## Прийняті рішення

- **Поділ балів за ТЗ.** Порівну між виконавцями, остача — по балу тим, хто взяв ТЗ раніше (10 на трьох: 4, 3, 3). Бали за ТЗ остаточні.
- **Статуси ТЗ:** Вільне → В роботі → На перевірці → Виконано; з перевірки можна повернути в роботу з коментарем. ТЗ лишається вільним,
  поки хтось із виконавців не натисне «Почати» (навіть коли всі місця зайняті): до того можна приєднатися й відмовитися.
- **Архів ТЗ.** Виконане ТЗ іде з дошки в архів: вручну (admin, moderator — одне чи «Усі виконані — в архів») або само через 30 днів
  після прийняття (сервер щогодини, `TasksService.autoArchive`; повернуте з архіву — через 30 днів після повернення). Архів —
  колонки `tasks.archived_at`, `archived_by_id` (`null` — сервер), `unarchived_at`; статус лишається `done`. Архівне ТЗ бачать усі
  (вкладка «Архів» на `/tasks`: пошук, тип та інші поля-довідники, рік прийняття — на сервері, сторінками); воно лишається в балах,
  профілі, документах і «Пов'язаному» з позначкою «в архіві». Архіву проєктів зі стадією «Завершено» поки немає.
- **Кошик і архів — різне.** «В архів» (файли Архіву, проєкти, статус обладнання) ховає й зберігає, сервер його не чіпає.
  «Видалити» — у кошик (колонки `deleted_at`, `deleted_by_id`): запис зникає скрізь, крім кошика й історії. Відновлюють admin і
  moderator; «Видалити назавжди» — admin або сервер через 90 днів (`TrashService.autoPurge`, щогодини). Із історією (рядки модуля,
  що посилаються на запис, і документи редактора, крім чернеток) лишається рядок із назвою й кодом (`purged_at`), інакше запис
  стирається з зв'язками й файлами. Код обладнання й позиції унікальний серед незатертих: у кошику зайнятий, після «назавжди» вільний.
  Кошик не знає розділів: модуль реєструє `TrashableType` (перевірки перед видаленням, що є історією, що стерти). ТЗ — лише архів
  (за ними бали), учасники — лише деактивація, довідники й шаблони — свій архів. Видалення обладнання скасовує його майбутні
  бронювання, позиції — списує залишок; підписаний скан документа редактора не видаляється.
- **Етапи проєкту:** Ідея → Планування → Виконання → Перевірка → Завершено; архів — окрема дія. ТЗ і проєкти пов'язуються через загальні зв'язки.
- **Забутий сеанс** закривається сам через 12 годин (`SESSION_AUTO_CLOSE_HOURS`) з позначкою «закрито автоматично».
- **Дисципліна** не має терміну дії: видається «Поданням про стягнення», знімається скасуванням подання з причиною
  (видане до документів — кнопкою «Зняти» на `/discipline`); знятий штраф повертає бали.
- **Ручні бали** нараховує «Відомість балів» (рядок — нарахування); одне нарахування з відомості не знімається — лише вся відомість
  її скасуванням з причиною (зроблене до документів — кнопкою «Зняти» на `/points`).
- **Списання зі складу** — «Акт списання» (рядок — позиція, кількість, причина); скасування акта повертає списане новими рухами.
  «Взяти» й «Поповнити» на сторінці позиції лишаються як були.
- **Допуск** видає «Запис про інструктаж і допуск»; повторний інструктаж — новий запис, що оновлює термін того самого допуску.
  Відкликає допуск скасування запису, який видав чинний термін (виданий до документів — кнопкою «Відкликати»).
- **Редактор документів.** Офіційні записи (ТЗ, стягнення, ручні бали, допуски, списання) створюються й змінюються лише через
  документ; робочі дії (взяти, почати, здати, прийняти ТЗ; сеанси, бронювання, склад) — у своїх розділах. Шлях документа однаковий
  для всіх: Чернетка → Опубліковано → Зафіксовано → Підписано, після публікації — Скасовано з причиною; опублікований документ не
  видаляється. Публікація не обходить права: через документ можна рівно те саме, що й без нього. Редактор не знає розділів —
  лише схеми записів, адаптери, читачі, джерела таблиць і довідники модулів. Спільного редагування наживо немає (автозбереження
  з `revision`). Друк — A4 книжкова, поля за ДСТУ 4163:2020, Times New Roman / Liberation Serif; PDF — «Друк → Зберегти як PDF»
  у браузері, DOCX — лише копія. Графічний підпис — внутрішнє підтвердження «це я» в DigiComp HUB, а не КЕП.
- **Акаунти** створюють модератор чи адмін з паролем; самостійної реєстрації немає. Перший адмін — через `POST /api/auth/setup`; разом із ним публікуються початкові шаблони редактора.

- **Бункер (правила).** 4–16 гравців, місць — половина з округленням униз. 5 раундів: ходи по черзі (у раунді 1 професія
  відкривається сама й гравець відкриває ще одну карту, далі — по одній), обговорення, таємне голосування. Вигнання — у раундах 2–5
  рівномірно, остача — на останні (`scheduleFor`). Нічия — переголосування між рівними, знову нічия — жереб сервера (`crypto.randomInt`).
  Час ходу вийшов або ведучий пропустив хід — відкривається випадкова закрита карта. Хто вийшов із кімнати, вибуває; вигнання, що
  лишилися, розподіляються заново, голосування починається знову. Особливі умови з дією виконує сервер (обмін, нова карта з колоди,
  відкрити чужу карту, подвійний голос, захист на раунд, перенести вигнання на наступний раунд), «без автоматики» — лише показується.
  Ведучий — той, хто створив кімнату (може лише вести); пішов — роль переходить до гравця, що ще в грі. Переможців і балів немає.
- **Бункер (сервер).** Реалтайму немає: сторінка питає раз на 2 с (у межах ліміту 300 запитів на хвилину), WebSocket не потрібен.
  Кожна дія — транзакція з блокуванням рядка кімнати; прострочений хід застосовується під час наступного запиту (таймерів у процесі
  немає, тож перезапуск API гру не ламає). Кімнату без дій 6 годин сервер видаляє (щогодини, `BunkerRoomsService.cleanup`).
  В аудит ідуть карти, паки, створення й закриття кімнат і вилучення гравця ведучим; ходи й голоси — лише в хроніку гри.

## Відкладено

- Принтери (паперові через CUPS, 3D — статус через HA): повернемось, коли будуть моделі й спосіб підключення.
- Telegram-бот і сповіщення.
- Запрошення за посиланням.
- Імпорт команди з CSV, антивірусна перевірка файлів.
- Редактор: спільне редагування наживо, PDF на сервері (Chromium), кваліфікований електронний підпис (КЕП).
- Архів проєктів зі стадією «Завершено» (як архів ТЗ) — окремо, якщо знадобиться.
- Бункер: екран для проєктора (лише відкрите, великим шрифтом), голосування вибулих «чи виживе бункер», статистика ігор у профілі,
  картинки на картах, інші ігри в «Розвагах».

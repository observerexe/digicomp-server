# Міграції бази даних

Схема бази змінюється лише через міграції (файли в `api/src/migrations`). Автоматична синхронізація схеми вимкнена,
тож зміна коду сама ніколи не видалить колонку з даними. Міграції застосовуються автоматично при старті API.

## Одноразове налаштування (базова міграція)

    cd ~/server
    ./scripts/migration-baseline.sh
    git add api/src/migrations
    git commit -m "api: baseline migration"
    docker compose up -d --build api

Базова міграція створює всю поточну схему на порожній базі. На базі, де таблиці вже є (як зараз), вона нічого не робить і лише
записується як виконана. Тому та сама міграція працює і на цьому сервері, і на новій машині з порожньою базою.

## Перевірка, що схема збігається з кодом

    ./scripts/schema-check.sh

## Як змінити схему

1. Зробіть резервну копію: `./scripts/backup.sh`
2. Змініть сутність у коді (колонку, таблицю).
3. Згенеруйте міграцію: `./scripts/migration-generate.sh НазваЗміни`
4. Відкрийте новий файл у `api/src/migrations` і прочитайте SQL.
   Перейменування колонки генератор записує як «видалити стару і створити нову», а це втрата даних: у такому разі замініть SQL на `ALTER TABLE ... RENAME COLUMN ...`.
5. Закомітьте файл і перезберіть API: `docker compose up -d --build api`

## Відкат міграції

Кожна міграція має метод `down`, але на практиці надійніше відновити базу з копії (див. `docs/BACKUP_UA.md`) і відкотити код через `git`.

## Журнал міграцій з особливостями

### `RenameCoordinatorRemoveGuest` (етап 1)

- Роль `coordinator` перейменовується на `moderator`. Рядки не переписуються: змінюється лише назва значення в типі `users_role_enum`.
- Роль `guest` прибирається. Кожен гість стає `member` з `active = false` (заблокований), його refresh-сеанси видаляються.
  На кожного такого користувача в `audit_log` пишеться запис `user.guest_converted` (у `meta` є `activeBefore`).
- Інших даних міграція не чіпає.
- `down` повертає `coordinator`, але колишніх гостей назад у `guest` не переводить: знайти їх можна в аудиті
  (`SELECT entity_id FROM audit_log WHERE action = 'user.guest_converted'`).
- Старий фронт (`digicomp-hub`) знає лише `coordinator`, тому розгортати цю міграцію на сервері треба разом із новим фронтом (етап 9 у `docs/PLAN.md`).

### `TasksPointsDiscipline` (етап 2)

- `task_assignees`:
  - колонки `tasksId`, `usersId` перейменовуються на `task_id`, `user_id`, рядки зберігаються;
  - додається `taken_at`: порядок взяття ТЗ, від нього залежить остача при поділі балів. Наявні рядки отримують час міграції.
- `tasks`:
  - у статус додано `queued` («В черзі»). Тип `tasks_status_enum` перестворюється, щоб нове значення можна було використати в тій самій транзакції;
  - вільні ТЗ (`todo`), у яких уже є виконавці, стають `queued`;
  - `max_assignees` = кількість виконавців, але не менше 1;
  - `updated_at` береться з `completed_at` або `created_at`.
- `points_ledger`:
  - додано `kind`: записи з `task_id` або `reason = 'task_completed'` стають `task`, решта `manual`;
  - додано `created_by_id` (для старих записів `NULL`, тому модератор їх зняти не може, лише admin) і `reverses_id`;
  - баланси не змінюються. Бали за вже виконані ТЗ не перераховуються: хто раніше отримав повну суму, той її і має.
- Нові таблиці: `discipline_records`, `task_comments`, `task_files` (файли лежать у `tasks/` у сховищі).
- `down`:
  - повертає стару схему, `queued` → `todo`;
  - записи книги балів (штрафи, компенсації) лишаються, тому баланси не змінюються;
  - дисципліна, коментарі та записи про файли ТЗ видаляються.
- Перевірено e2e-тестом `api/test/migration-tasks.e2e-spec.ts`.
- Старий фронт змінює статус ТЗ через `PATCH /tasks/:id/status`, а цей шлях прибрано. Тому розгортати разом із новим фронтом (етап 9).

### `LabBookingsFaultsProjectStages` (етап 3)

- Вмикає розширення `btree_gist`. Воно потрібне, щоб база сама забороняла перетин бронювань одного обладнання (обмеження `bookings_no_overlap`). Розширення входить в образ `postgres:17-alpine`.
- Нові таблиці: `bookings`, `fault_reports`, `fault_photos` (фото лежать у `faults/` у сховищі).
- `work_sessions.auto_closed`: для наявних сеансів `false`, самі сеанси не змінюються. Після розгортання сервер протягом 10 хвилин закриє всі відкриті сеанси, старші за 12 годин.
- `projects.status` (вільний текст) замінено на `stage` (фіксований етап). Етап визначається за ключовими словами без урахування регістру:
  - `заверш`, `готов`, `виконано`, `закінч` → `done`;
  - `перевір`, `тест`, `рев'ю` → `review`;
  - `робот`, `викон`, `процес`, `актив` → `execution`;
  - `ідея` → `idea`;
  - решта → `planning`.

  Перед видаленням колонки текст кожного проєкту пишеться в `audit_log` (`project.stage_migrated`, `meta.oldStatus`), тож нічого не губиться:
  `SELECT entity_id, meta FROM audit_log WHERE action = 'project.stage_migrated'`.
- Додано `projects.start_date`, `projects.deadline` (тип `date`).
- `down` відновлює текстовий статус з етапу («Планується», «В роботі» тощо; оригінал лишається в аудиті). Бронювання, звіти та фото видаляються.
- Перевірено e2e-тестом `api/test/migration-lab.e2e-spec.ts`.

### `TwoFactorAuth` (етап 4)

- Додає в `users` поля 2FA:
  - `totp_secret_enc` — секрет, зашифрований ключем `TOTP_KEY`;
  - `totp_enabled_at`, `totp_last_step`, `totp_failed_attempts`, `totp_locked_until`;
  - `recovery_codes` — хеші argon2.
- Додає `mfa` у `refresh_sessions`: чи пройшла ця сесія 2FA.
- Лише нові колонки зі значеннями за замовчуванням; наявні дані не змінюються, 2FA ні в кого не вмикається.
- `down` видаляє ці колонки: увімкнена 2FA зникає, користувачі входять лише за паролем.
